# RFC-021 — `.anet` artifact drift 自动修复

Status: Draft outline
Owner: 通信牛
Date: 2026-05-27
Scope: research/design only; no implementation in current patch
Related: PR #188, PR #189, Known Limits R3, Vincent telegram 5998

## 1. 背景

R3 暴露的问题不是 Grok Build ACP 单点 bug，而是 Agent Network 把一部分运行时协议面复制到了用户项目目录后，没有把这些文件当成有版本的受管 artifact 管理。

当前相关文件：

- `.anet/node-server.js`：项目本地 MCP stdio server，可被 Claude Code / MCP client 读取。
- `.mcp.json`：项目 MCP 配置，通常把 `commhub` server 指到 `.anet/node-server.js`。
- `.anet/nodes/<node>/config.json`：节点运行配置，token、runtime、session 等用户状态放这里。

R3 的具体症状：

1. 老版本 `anet` 写过 `.anet/node-server.js` 和 `.mcp.json`。
2. 后续升级 `@sleep2agi/agent-network` / `@sleep2agi/agent-node`。
3. 老 `.anet/node-server.js` 仍留在项目目录，工具 schema 不含 `commhub_get_task`、`parent_task_id` 等字段。
4. Grok / Claude 看到的 MCP tools 是 stale 版本，跨 agent 显式 delegation chain 可能静默断裂。
5. 当前 workaround 是手动删除 `.anet/node-server.js` 后重建节点或重跑初始化。

这个问题的核心是：`agent-network` 的协议面已经进化，但项目内受管 artifact 没有明确的 source of truth、schema version、reconcile 时机和漂移检测。

## 2. 当前实现观察

当前 CLI 有两条生成路径：

1. `anet init project` 路径只在 `.anet/node-server.js` 不存在时复制本地 server 文件；存在时直接跳过。
2. `ensureMcpJson(profile)` 有“每次更新 `.anet/node-server.js`”的意图，但它只在 `claude-code-cli` 且 profile 启用了 commhub channel 时执行。
3. `codex-sdk`、`claude-agent-sdk`、`grok-build-acp` 走 `agent-node` wrapper 分支时，`launchAgent()` 会调用 `ensureMcpJson(profile)`，但该函数开头直接 return，因此 SDK/Grok 节点启动不会刷新 `.anet/node-server.js` / `.mcp.json`。
4. `.mcp.json` 的写入逻辑既有“只在没有 commhub 时写”的分支，也有后续无条件覆盖 `mcpServers.commhub` 的分支；缺少“只管理自己 owns 的 commhub entry、保留其他 MCP server、识别 stale commhub entry”的明确契约。
5. `launchAgent()` 对 SDK/Grok runtime 查找 `agent-node` 的策略是 PATH 优先，找不到才 fallback 到 `npx -y @sleep2agi/agent-node@preview`。如果用户有旧 global `agent-node`，就可能 shadow 当前 preview/latest 期望版本。

结论：R3 不是单纯“用户忘了删文件”，而是 artifact lifecycle 没有被纳入 `anet node start` 的必经启动前校验。

## 3. 目标

本 RFC 的目标是定义下一轮实现方向，使 `anet` 自动避免或修复 `.anet` artifact drift。

必须满足：

- `anet node start <name>` 启动前自动检查并修复受管 artifact。
- `.anet/node-server.js` 和 `.mcp.json` 作为一组 artifact reconcile，避免只修一个文件。
- 不删除用户其他 MCP server 配置。
- 不触碰 `.anet/nodes/<node>/config.json` 内的 token、session、runtime 等用户状态。
- 旧 `atok_` token 兼容不被本 RFC 破坏；token 修复属于已有 `doctor`/node lifecycle 问题。
- 对 stale schema 给出可诊断日志，不再让 delegation chain 静默断裂。
- 所有实现先走 Docker E2E，再 publish。

非目标：

- 当前 v0.10.x broaden patch 不被本 RFC 阻塞。
- 不在当前 patch 里实现。
- 不把 Grok native MCP tool injection 作为稳定路径的前提。

## 4. 受管 artifact 定义

建议新增 artifact source of truth 概念：

- 源：当前正在运行的 `@sleep2agi/agent-network` 包内 `dist/src/node-server.js`，开发模式 fallback 到 `agent-network/src/node-server.ts`。
- 目标：项目目录 `.anet/node-server.js`。
- 配套配置：项目目录 `.mcp.json` 中由 anet 管理的 `mcpServers.commhub` entry。
- 元数据：`.anet/artifacts.json` 或文件 banner 中记录 package version、schema version、hash。

示例 banner（code 例子保持英文）：

```js
// Generated by @sleep2agi/agent-network. Do not edit by hand.
// artifact: commhub-node-server
// package: @sleep2agi/agent-network@2.2.9-preview.0
// schema: commhub-mcp-tools@3
// sourceHash: sha256:...
```

示例 manifest：

```json
{
  "version": 1,
  "artifacts": {
    "nodeServer": {
      "path": ".anet/node-server.js",
      "package": "@sleep2agi/agent-network",
      "packageVersion": "2.2.9-preview.0",
      "schemaVersion": "commhub-mcp-tools@3",
      "sha256": "sha256:..."
    },
    "mcpJson": {
      "path": ".mcp.json",
      "managedServers": ["commhub"]
    }
  }
}
```

## 5. 方案评估

### Option A — 每次 `anet node start` 自动重写

做法：在 `launchAgent()` 早期统一调用 `reconcileProjectArtifacts(profile)`，不再只对 `claude-code-cli + commhub channel` 生效。每次启动都从当前 `agent-network` package 复制 `.anet/node-server.js`，并 idempotent 合并 `.mcp.json`。

Pros:

- 最简单，最能直接消灭 stale `.anet/node-server.js`。
- 用户无需知道 `.anet/node-server.js` 的存在。
- 不会触碰 `.anet/nodes/<node>/config.json`、token、session。
- 对 Grok runtime 有直接帮助，即使 Grok 当前稳定路径是 wrapper delegation，也不会让项目 MCP tool schema 留在旧状态。

Cons:

- 如果用户手动改过 `.anet/node-server.js`，会被覆盖。需要明确该文件是 generated artifact。
- 每次启动写文件会造成 git working tree 变化，尤其用户把 `.anet` 误加入 git 时会明显。
- 仅靠重写无法解释“为什么要重写”，诊断能力弱。

Complexity:

- LOC: 60-100。
- Risk: low-medium。主要风险是误覆盖用户自定义 `.anet/node-server.js` 或 `.mcp.json` commhub entry。

`.mcp.json` 联动:

- 必须同一函数内处理 `.mcp.json`。
- 只更新 `mcpServers.commhub`，保留其他 server。
- 如果存在旧 `commhub` entry 但 command/args 不指向 `.anet/node-server.js`，应识别为 drift 并修复，除非用户显式标了 unmanaged。

Schema versioning:

- 不强制需要，但建议同时加 hash/baseline 日志，否则未来仍难诊断。

### Option B — Version stamp + mismatch diff 后刷新

做法：在 `.anet/node-server.js` 顶部写入版本 banner，或在 `.anet/artifacts.json` 写入 manifest。启动时比对 package version、schema version、source hash；不一致才重写。

Pros:

- 减少无意义写文件。
- 日志可解释：`schema commhub-mcp-tools@2 -> @3, refreshed`。
- 方便 `anet doctor` 和 dashboard 显示 drift 状态。
- 可区分 package semver 与工具 schema 版本，避免每个 patch 都强制认定 incompatible。

Cons:

- 老版本 artifact 没有 stamp，需要 fallback heuristic。
- 需要维护 `ANET_ARTIFACT_SCHEMA_VERSION` 或 `COMMHub_MCP_SCHEMA_VERSION`。
- 实现比 Option A 复杂。

Complexity:

- LOC: 120-180。
- Risk: medium。主要风险是 schema version 维护不严导致 false fresh。

`.mcp.json` 联动:

- manifest 应记录 managed MCP server name 和期望 command/args。
- `.mcp.json` 本身不能安全加注释，推荐把元数据放 `.anet/artifacts.json`。

Schema versioning:

- 需要。建议独立于 npm package version，例如 `commhub-mcp-tools@3`。

### Option C — `PINNED_AGENT_NODE_VERSION` / 启动版本钉死

做法：`agent-network` CLI 内显式维护 `PINNED_AGENT_NODE_VERSION`，`launchAgent()` 不再使用裸 `agent-node` 或 `@preview` fallback 作为唯一策略。至少在 preview/stable 发布时明确 agent-network 与 agent-node 的兼容矩阵。

Pros:

- 解决“全局旧 `agent-node` shadow 当前预期版本”的 split-brain。
- preview smoke 更可复现。
- 与 release SOP 中 promote latest 后 bump pinned version 的节奏一致。

Cons:

- 不能单独解决 `.anet/node-server.js` stale；它修的是 runtime binary 版本，不是项目 artifact。
- 维护成本增加，每次 release 需要同步 bump。
- 如果用户明确想本地源码调试 `agent-node`，需要 override。

Complexity:

- LOC: 40-80。
- Risk: medium。风险在安装路径、npx 行为、preview/latest policy 和本地开发 override。

`.mcp.json` 联动:

- 无直接联动，但能减少“agent-node 已升级、agent-network artifact 未升级”这种组合漂移。

Schema versioning:

- 不需要，但应和 Option B 的 artifact schema 一起记录兼容矩阵。

### Option D — MCP server self-introspection

做法：让 runtime 启动时主动 query MCP server tools 列表，或让 Grok/agent-node 不依赖 `.anet/*` 静态配置，而是通过 runtime 内部 MCP client 动态获取工具 schema。

Pros:

- 从架构上减少对项目内静态复制文件的依赖。
- 能在启动期发现 `commhub_get_task`、`parent_task_id` 缺失并 fail fast。
- 为未来多 MCP server、远程 MCP、dashboard 可视化 tools schema 做基础。

Cons:

- 改动深，涉及 runtime、MCP client、Claude/Grok/Codex provider 差异。
- 当前 Grok 稳定支持路径是 `agent-node` wrapper explicit delegation，不应为了 R3 把 native MCP injection 变成 blocker。
- 仍不能完全绕过 `.mcp.json`，因为 Claude Code 等外部 client 还是读取项目 MCP 配置。

Complexity:

- LOC: 250-500+。
- Risk: high。适合 v0.11+ 架构迭代，不适合作为 R3 的首个修复。

`.mcp.json` 联动:

- 对 wrapper runtime 可减少依赖；对外部 MCP client 仍需保留 `.mcp.json` 管理。

Schema versioning:

- 需要。运行时 introspection 仍要知道 minimum required tool set。

### Option E — 手动 workaround + better error

做法：不自动修，只在启动时检测 stale schema，打印明确错误和修复命令，例如 `anet doctor --fix-artifacts` 或 `rm .anet/node-server.js && anet init project`。

Pros:

- 改动最小。
- 避免自动覆盖用户本地文件。
- 可作为 Option A/B 的 fallback。

Cons:

- 没有满足 Vincent “自动避免/修复 root cause” 的要求。
- 用户仍需理解内部文件，体验不达标。
- 如果只 warn 不 fail，delegation 仍可能静默坏。

Complexity:

- LOC: 40-70。
- Risk: low。

`.mcp.json` 联动:

- 检测时必须同时检查 `.mcp.json` entry 是否指向 stale/错误路径。

Schema versioning:

- 建议需要，否则 stale 检测只能 grep tool name，脆弱。

### Option F — Manifest + `anet doctor --fix-artifacts`

做法：新增显式管理命令：

```bash
anet doctor --artifacts
anet doctor --fix-artifacts
```

`node start` 自动执行 lightweight reconcile；`doctor` 提供可见诊断和手动修复入口。

Pros:

- 启动自动修复和用户可理解性兼得。
- QA / support 可以要求用户贴 doctor 输出，不再让用户手动 diff `.anet`。
- 可以渐进接入更多 artifact，例如 channel config、dashboard project metadata。

Cons:

- 命令面扩大。
- 需要把 artifact 状态定义清楚，避免 doctor 成为杂项脚本。

Complexity:

- LOC: 100-160。
- Risk: medium-low。

`.mcp.json` 联动:

- 是该方案的核心输出之一，应明确显示 managed/unmanaged、fresh/stale、fixed/skipped。

Schema versioning:

- 需要。

## 6. 推荐方案

推荐下一轮采用组合方案：A + B + E 的最小闭环，C 作为 release hygiene 同步推进，D 延后。

P0 实现：

1. 新增 `reconcileProjectArtifacts({ mode })`。
2. `anet node start <name>`、`anet init project`、`anet doctor --fix` 都调用它。
3. 每次启动前检查 `.anet/node-server.js` 与当前 package source hash。
4. drift 时自动刷新 `.anet/node-server.js`。
5. 同步 merge `.mcp.json` 的 `mcpServers.commhub`，保留用户其他 MCP server。
6. 对老无 stamp 文件：如果内容匹配 Agent Network generated server 特征，自动覆盖；如果无法确认，先备份到 `.anet/node-server.js.bak.<timestamp>` 后再写入，并打印日志。
7. 启动日志输出一行 concise 状态：fresh/refreshed/skipped。

P1 实现：

1. 增加 `.anet/artifacts.json` manifest。
2. 增加 `COMMHub_MCP_SCHEMA_VERSION` 或 `ANET_ARTIFACT_SCHEMA_VERSION` 常量。
3. `anet doctor --artifacts` 输出 artifact 状态。
4. 添加 Docker drift E2E。

P2 实现：

1. 明确 `PINNED_AGENT_NODE_VERSION`。
2. `launchAgent()` 对 PATH 中旧 `agent-node` 做版本检查，低于 pinned 时优先 npx pinned 或 fail with fix。
3. preview/stable release SOP 中把 pinned bump 变成 gate。

暂不推荐把 Option D 放入 R3 修复，因为它风险高、覆盖面大，而且不能替代 `.mcp.json` 对外部 MCP client 的配置需求。

## 7. 具体设计草案

建议抽象：

```ts
type ArtifactReconcileMode = "check" | "fix";

type ArtifactReconcileResult = {
  nodeServer: "fresh" | "refreshed" | "missing-source" | "skipped-unmanaged";
  mcpJson: "fresh" | "updated" | "invalid-json" | "skipped";
  schemaVersion: string;
  sourceHash?: string;
};

function reconcileProjectArtifacts(mode: ArtifactReconcileMode): ArtifactReconcileResult {
  // 1. Resolve package source.
  // 2. Compare .anet/node-server.js by hash/stamp.
  // 3. Write atomically when stale and mode === "fix".
  // 4. Merge .mcp.json commhub entry without deleting unrelated servers.
  // 5. Persist .anet/artifacts.json.
}
```

`.mcp.json` merge 规则：

- 保留所有非 anet 管理的 `mcpServers.*`。
- `commhub` entry 是 anet 管理的默认名字。
- 如果 `commhub` entry 不存在，新增。
- 如果 `commhub` entry 存在且指向 `.anet/node-server.js` 旧形态，更新。
- 如果 `commhub` entry 存在但明显是用户自定义 server，备份原 entry 到 `commhub_custom` 或提示冲突；不要静默删除。
- JSON parse 失败时不覆盖，输出 fail-fast 错误，引导用户修 `.mcp.json`。

原子写：

```ts
function atomicWrite(path: string, content: string): void {
  const tmp = `${path}.tmp-${process.pid}`;
  writeFileSync(tmp, content);
  renameSync(tmp, path);
}
```

## 8. 测试计划

新增 Docker 测试套件建议：`tests/test-anet-artifact-drift/`。

分层测试：

1. 环境层：安装指定 `@sleep2agi/agent-network` 和 `@sleep2agi/agent-node`，确认 `anet --version`、`agent-node --version`。
2. 认证层：本地 CommHub 启动，创建 node token，避免真实生产 token。
3. 单点 artifact 层：
   - 准备旧 `.anet/node-server.js`，内容不含 `commhub_get_task`。
   - 准备旧 `.mcp.json`，`commhub` args 指向旧路径或缺失。
   - 执行 `anet node start <node> --dry-run-artifacts` 或 `anet doctor --fix-artifacts`。
   - 验证 `.anet/node-server.js` 含 `commhub_get_task` 和 `parent_task_id`。
4. 完整流程层：
   - 创建 Grok/codex mock runtime 节点。
   - 模拟 explicit delegation chain。
   - 验证 parent task_id 被带入。
5. 多用户/兼容层：
   - `.mcp.json` 内有 unrelated MCP server，修复后仍保留。
   - 旧无 stamp artifact 可被修复。
6. 安全层：
   - `.mcp.json` invalid JSON 时 fail fast，不覆盖。
   - 手工 unknown `.anet/node-server.js` 被备份后替换，日志明确。

测试报告保存到：


## 9. 安全和兼容性

`.anet/node-server.js` 是可执行 JS，长期 stale 本身就是风险：用户以为升级了 `anet`，实际执行的是项目里旧代码。自动 reconcile 会降低旧代码长期驻留的概率。

兼容性策略：

- `.anet/nodes/<node>/config.json` 不改。
- `.anet/.env` 仅沿用现有逻辑，不在本 RFC 扩大 token 处理范围。
- `.mcp.json` 只改 anet 管理的 commhub entry。
- 对无 stamp 的历史 artifact 做 best-effort 识别；不能识别时备份再写，不直接丢弃。
- 所有修复写入前后输出简短日志，方便用户知道发生了什么。

需要避免：

- 把 `.mcp.json` 整文件重写成只剩 commhub。
- 因为 preview/latest 切换，让用户稳定版本突然拉到 preview。
- 用 package semver 直接代表 tool schema compatibility；schema version 应独立。

## 10. Open Questions

1. `.anet/node-server.js` 是否应被视为完全 generated，不支持用户编辑？建议答案：是。
2. `.mcp.json` 中 anet 管理的 server 名是否固定为 `commhub`？建议答案：默认固定，未来多 hub 再引入命名空间。
3. 对旧 global `agent-node` shadow 的策略是 warn、fail，还是 npx pinned override？建议在 P2 由 release owner 定。
4. `anet node start` 是否需要 `--no-artifact-refresh` debug flag？建议只给内部/debug 用，不写入主文档。
5. `doctor --fix` 是否统一修 token、artifact、node_id，还是拆成 `--fix-artifacts`？建议先拆，避免隐藏副作用。
