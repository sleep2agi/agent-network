# RFC-041 节点(Agent)自己的权限

> 状态:**草案**(看板 #487)。只有设计,没有代码。Owner 原话:「节点它自己的权限…你先设计一下」;让我们自己定,下面每一条都是**推荐**,不是问题。
> 相关:RFC-038(成员 × Agent / 任务权限)、RFC-040(部门负责人)、#2086(节点令牌不再继承主人的管理员权限)、#469 MCP 审计。

## 0. 结论先行

- **节点的权限 = 它主人权限的子集,永远不超过主人**;再按节点自己的「模式」往下收。
- 三种模式,主人在 app 里给每个节点设:**正常**(默认)/ **只读** / **受限**(只碰派给它的任务)。
- 人才能做的事,节点一律不能:邀请 / 移出成员、改角色、建 / 改 / 删项目、改组织架构、删任务、改任何权限。
- **先记录、后执行**:第一步只记「本来会被拒」的写(节点、路由、原因),看报表;确认没有误伤再按开关执行。
- 生产实测(§3.1):按「正常」规则执行,**最近 43 小时的 325 次节点写入一次都不会被拒**;只有主动设成「受限」才会拦,对应 81 次(2 个节点)。

## 1. 今天(origin/main a7d73b02 的代码)

| 能力 | 节点令牌今天能做什么 | 代码 |
|---|---|---|
| 读任务 | 本网络**全部**任务,不经过任务可见性(`taskCaller()` 对节点令牌返回 null) | `requirements.ts` |
| 写任务 | 建、改、勾检查项、upsert、评论:**本网络任何一张** | `NODE_TOKEN_OPERATIONS` |
| 删任务 | 不能(403 `user_token_required`) | 同上 |
| 项目 | 只读;建 / 改 / 归档 403 | `operationOf()` |
| 人 / 部门 | 读通讯录(`requirements_people`)和组织架构;不能改 | `departments.ts` |
| 派活 / 发消息给别的 Agent | 主人不受限:网络内任意 Agent。**主人是受限成员**(`agent_access=granted`):节点的**一切写**(派活、发消息、甚至 `report_status` 心跳)都被 `canWrite` 以 `permission_denied`「Viewer role…」拒掉 —— 过度拒绝,错误文案也不对 | `tools.ts` `canWrite` → `canRestWriteNetwork`(按铸令牌的用户判受限) |
| 读名册 / 任务流水 | 主人受限时**仍看得到全网 Agent**:`restrictedNets` 只对用户令牌计算,节点令牌的读不按主人的授权收窄 | `tools.ts` registerTools(`restrictedNets`) |
| 管理节点(启停、规则、配置) | 只能管自己(按 node_id 绑定) | #2086、RFC-036 |

两个缺口(10-02 #488 实测更正:最初写的「受限成员的节点能向任何 Agent 派活」**不成立** —— 是从 `restrictedNets` 推出来的,没跟到 `canWrite`;实测这类节点的写全部被拒):

1. **主人受限时,节点的读超出主人、写又被一刀切。** 读:名册 / 任务流水看得到全网 Agent;写:连心跳都被拒(错误文案还写成「Viewer role」)。两头都不对 —— 应当是「读和写都等于主人的授权」。生产上目前没有这样的节点:最近 7 天派过活的 20 个节点全部由不受限的网络 owner 铸造;受限成员也铸不了新令牌(`createNetworkTokenForNode` 拒绝)。只有「先铸令牌、后被收窄」的成员会碰到。
2. **写的范围没有收窄的办法。** 一个只该做同步的节点可以改任何一张卡的描述;主人想「只让它碰派给它的活」没有开关。

## 2. 设计

### 2.1 主人是谁

节点的主人 = `nodes.owner_user_id`(RFC-036,建节点时定死)。老节点没有这一列时,取**铸这个节点令牌的用户**(`api_tokens.user_id`;#462 用的同一条规则)。两者都没有 → 当作「只读」节点,并在日志里记 `owner_unknown`。

### 2.2 权限矩阵(节点 vs 主人)

「主人能」= 主人按 RFC-038 / RFC-040 实际有的权限(角色、`task_access`、按人 / 按部门项目授权、负责人身份)。节点在此基础上再受模式约束:

| 动作 | 主人 | 节点 · 正常 | 节点 · 只读 | 节点 · 受限 |
|---|---|---|---|---|
| 读任务 | 按他的可见范围 | **= 主人的可见范围** | = 主人的可见范围 | 派给它的(负责 Agent 是它 / 参与人有它 / 它建的)+ 这些卡的子任务 |
| 建任务 | 按他的权限 | 主人能建的地方能建 | 不能 | 能建,但必须把自己设为负责 Agent |
| 改任务 / 勾检查项 / upsert | 按他的权限 | 负责 Agent 是它、参与人有它、它建的,**或主人能改的** | 不能 | 只有派给它的 |
| 评论 | 看得见且非只读 | 看得见就能评 | 不能 | 只在派给它的卡上 |
| 删任务 | 按他的权限 | **不能** | 不能 | 不能 |
| 项目:读 | 按他的授权 | = 主人 | = 主人 | 只看派给它的卡所在的项目 |
| 项目:建 / 改 / 归档 | owner/admin、`all` 成员 | **不能** | 不能 | 不能 |
| 人 / 部门:读 | 能 | 能(Agent 只列主人看得见的) | 能 | 能 |
| 人 / 部门 / 角色 / 邀请 / 权限:改 | 按角色 | **不能** | 不能 | 不能 |
| 派活 / 发消息给别的 Agent | 按他的 Agent 授权 | **= 主人的 Agent 授权**(修正缺口 1:今天受限主人的节点被全部拒绝) | 不能派活;可以回复派给它的任务 | 只能派给主人授权的 Agent;回复照常 |
| 回复 / ack / 上报状态 / 心跳 | — | 能 | 能 | 能 |
| 管理别的节点 | 按 RFC-036 | 不能 | 不能 | 不能 |

规则:**节点的权限 = 主人的权限 ∩ 模式允许的**。不会因为是节点而多出任何东西;「负责 Agent 是它 / 参与人有它」只是在主人**看得见**的前提下额外允许写。

### 2.3 三种模式

- **正常(默认)**:等于今天的绝大多数情况,只多两条收紧:不超出主人的可见 / Agent 授权;不能删、不能管项目(今天已如此)。
- **只读**:能读、能回复派给它的任务、能上报状态;不能写任务、不能派活。给「只看不动」的观察型 Agent。
- **受限**:只看、只写派给它的任务;派活只能给主人授权的 Agent。给外部 / 不太信任的节点。

模式存在节点上,只有主人和网络 owner/admin 能改;节点自己不能改自己的模式。

### 2.4 与 RFC-040(部门负责人)

- 部门负责人看本部门成员的 Agent(RFC-040 §1):**只看状态和健康**,不因此获得派活 / 对话权限;也**不能改这些节点的模式**(模式归节点主人和管理员)。
- 节点的权限按**它主人**的权限算。主人是部门负责人时,他的节点也能改本部门的任务(因为主人能改);但**不能删** —— 节点永远不能删任务(表里「删任务」一行),负责人的删除权不传给节点。
- 负责人的「管理本部门」界面里,成员的 Agent 行显示模式徽标(正常 / 只读 / 受限),只读。

## 3. 迁移:不让任何东西突然坏

### 3.1 生产实测(只读,管理员令牌,2026-10-02)

数据:生产 Hub 的任务动态(`requirement_events`,.77 起才有),窗口 **2026-09-30 19:53Z → 10-02 15:00Z(约 43 小时)**;1 个网络,5 个成员,276 个节点,487 张卡,564 条动态。

| 指标 | 数 |
|---|---|
| 节点写请求(按 节点 × 卡 × 时刻 合并) | **325**(356 条字段级动态),来自 **4** 个节点 |
| 其中:改它自己建的卡 | 213 |
| 其中:它是负责 Agent | 31 |
| 其中:都不是(改别人的卡) | 81(2 个节点:79 + 2;72 次是改描述) |
| **按「正常」执行会被拒** | **0** —— 5 个成员 `task_access` 都是 `all`,主人能改所有卡,节点也就能改 |
| 按「只读」执行会被拒 | 325(全部;只读本来就不该给写节点) |
| **按「受限」执行会被拒** | **81 / 325(25%)**,集中在 2 个节点 |

限制:① 只有 43 小时的数据(动态表 .77 才上线);② 用的是**现在**卡上的负责 Agent / 参与人,不是写入那一刻的;③ 读和派活没有流水,这里量不到 —— 这正是记录阶段要补的。④ 缺口 1:#488 实测,最近 7 天 8,422 个任务里 1,485 个由节点派出,来自 20 个节点,全部由不受限的网络 owner 铸造 —— 按「主人的 Agent 授权」执行,**0 个**会被拒。

### 3.2 三步

1. **只记录(Hub 一个版本)**:所有节点请求照常放行;按 §2 规则判一遍,「本来会被拒」的写一行 `node_permission_would_deny`(节点 id、路由 / MCP 工具、规则、原因:`beyond_owner_visibility` / `agent_not_granted_to_owner` / `mode_readonly` / `mode_restricted_not_assigned` / `human_only` / `owner_unknown`)。按 (节点, 路由, 原因) 每小时合并一行,不刷表。
2. **报表(同版本或下一版)**:`GET /api/networks/:id/node-permission-report?since=` 给 owner/admin:按节点、原因计数 + 最近样例(卡号、工具)。app 设置 → 节点权限页顶部显示「过去 7 天若开启会拦 N 次」。
3. **执行(开关)**:Hub 环境变量 `COMMHUB_NODE_PERMISSIONS=enforce`(默认 `log`);确认 7 天报表没有误伤后再切。执行时的拒绝:REST 403 / MCP 错误,`error: "node_permission_denied"` + `field`/`reason`/`hint`(走 #472 的 `errorBody`),hint 写明「请节点主人在 app 里把模式改为正常,或把任务派给这个节点」。

模式本身(只读 / 受限)由主人主动设置,**设了就立刻生效**,不受上面的开关影响 —— 主人设它就是要它生效;开关只管「正常模式下补上缺口 1 的那两条收紧」。

## 5. 推荐的决定(owner 让我们自己定)

1. **节点权限 ≤ 主人权限**,包括 Agent 授权(补上缺口 1)。
2. **默认「正常」**,升级零变化;只读 / 受限由主人主动设,设了即生效。
3. **节点永远不能删任务、不能管项目 / 成员 / 部门 / 权限。**
4. **先记录 7 天再执行**;执行开关在 Hub 环境变量,默认 `log`。
5. **部门负责人对成员的 Agent 只看不管**,不能改它们的模式(与 RFC-040 一致)。
