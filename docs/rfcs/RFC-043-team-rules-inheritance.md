# RFC-043 全团队规则的继承与注入（Hub → Daemon → 节点）

> 状态：**草案 / Draft（2026-10-24）**。上游：#1521（全团队规则）/ #1542（存储片，已随 `.153` 上线）/ #993。
> 本文只讨论**继承与注入**；存储与 REST 权限已经在生产（`network_rules` 表 + `GET/PUT /api/networks/:id/rules`）。
> **本文不写代码**：三个产品决定未定之前，任何实现都是在替人拍板。

## 0. 结论先行

1. **注入方式是「受管块」而不是「生成新文件」**：claude 只读 `CLAUDE.md`，其余运行时只读 `AGENTS.md`
   （`agent-node/src/runtime/rules-file.ts`），生成一个旁路文件不会被任何运行时读到。所以要进入这两个文件，
   但**只在一个带标记的块内**改写，块外内容一个字节都不动。
2. **优先级：拼接 + 最具体层生效**（同一条冲突声明以最具体层为准）。理由见 §2。
3. **注入时机：节点完整启动时拉一次**（v1 不做运行中推送）。理由见 §4。
4. **Hub 不可达时用「上次已应用」的内容并显式告警**，不静默降级为无规则。
5. **三个待决问题**（§8）各有推荐默认值；回答任意一个就能开工对应的那一行。

## 1. 现状（读代码得出，2026-10-24 main）

| 东西 | 在哪 | 与本文的关系 |
|---|---|---|
| 网络规则存储 | `server/src/network-rules.ts`，表 `network_rules(network_id PK, content, revision, …)` | 第一层（Hub）的来源；`.152` 起 revision **幂等**（同内容不涨） |
| REST | `GET/PUT /api/networks/:id/rules`（CAS `expected_revision`，256 KiB，节点令牌只读自己的网络） | Hub 侧的读写面 |
| 节点规则文件 | `agent-node/src/runtime/rules-file.ts`：`claude → CLAUDE.md`，其余 → `AGENTS.md`，路径 = 节点 cwd | 注入的落点 |
| 远程改写 | MCP `write_node_rules_file`（Hub 门铃 `{type:"rules_file"}` → 节点拉取 → 写文件 → ack），**无路径参数**，上限 256 KiB | 已有的推送通道；v2 才会用到 |
| 节点环境 | daemon 注入的 env、`config.json` | 第二层（Daemon）的来源 |

> 关键约束：**没有任何运行时支持 include**。所以「继承」在物理上只能是**一个文件内的合并文本**。

## 2. 三层与冲突语义

### 2.1 分层
```
Hub（network_rules，全网）  →  Daemon（该宿主上的所有节点）  →  节点（自己那份文件）
```
Daemon 层需要新存储（一张 daemon 规则表）与一个写面，属**第二片之外**；本文先把三层语义定死，实现可以只做 Hub + 节点两层，Daemon 层留空。

### 2.2 候选语义
| 方案 | 含义 | 问题 |
|---|---|---|
| A 具体优先（覆盖） | 节点 > Daemon > Hub，后层整段替换前层 | 团队规则通常互补，覆盖会让上层大半内容白写 |
| B 中心优先 | Hub 覆盖一切 | 人在节点上的就地收紧会被无声失效 |
| C 只拼接 | 按 Hub → Daemon → 节点拼成一份 | 冲突声明（MUST / MUST NOT）会同时出现两条相反要求，模型只能猜 |

### 2.3 推荐：C 的形态 + A 的裁决
- **文本层面拼接**（带来源标题与 revision，见 §3），保证每层内容都被读到；
- **冲突层面按「最具体层生效」**：同一主题出现相反声明时，越靠近执行面的越优先；
- 不做自动语义分析：只在**显式标记**上裁决（见 §3.2），其余冲突原样保留 + 在 provenance 里列出条目数，让人能看见。

这条推荐写成了「可被推翻的默认值」，不是不可讨论的结论。

## 3. 受管块（注入形态）

### 3.1 形状
```markdown
<!-- ANET:TEAM-RULES v3 BEGIN — 由 CommHub 自动维护，块外内容不会被修改 -->
## 团队规则（CommHub · Hub rev 3 / 节点 rev 1）

### 来源：Hub（网络 xxx，revision 3，更新于 2026-10-24T13:00Z）
<Hub 规则正文>

### 来源：节点（本文件原有内容，未搬移）
见块外。

<!-- ANET:TEAM-RULES v3 END -->
```
规则：
- 块**只**放在文件顶部；块外一切内容视为用户所有；
- 标记行缺失 → **追加**一个新块；标记成对存在 → **整块替换**；只有一半 → **拒绝写入并报错**（不猜测，避免吃掉用户内容）；
- 写入走既有原子写（`rules-file.ts` 已是原子写），失败不留下半个块；
- 同一 revision 重复注入 → 内容逐字节相同，**不产生 diff**（与 `.152/.153` 的幂等 revision 配套）。

### 3.2 显式标记（用于裁决）
块内每条声明前可带标记，v1 只识别两种：
```
[MUST] …        更具体层可以追加；上层写了、下层没写 → 保留
[MUST NOT] …    更具体层可以追加；上层写了、下层写相反 → 以更具体层为准，并在 provenance 里记一条 "overridden"
```
不做的是：语义推断（不解析自然语言意图）。

## 4. 时机与缓存

- **v1：节点完整启动时拉一次**（`GET /api/nodes/:id/rules` 待新增，或复用 Hub 现有接口）。
  理由：与 env 同口径（改 env 也要重启），可预测、可回滚；
  运行中改写规则文件会让正在跑的一轮读到半新半旧的内容。
- **v2（另评）：Hub 门铃推送**（复用 `write_node_rules_file` 通道），前提是客户端能显示"规则已更新，下一轮生效"。
- 节点侧记住 **最后应用的 revision**（写进 `config.json` 或旁路状态文件），用于：
  1. revision 未变 → 跳过写入（避免无意义 diff）；
  2. 审计"这一轮用的是哪版规则"。

## 5. 失败模式

| 情况 | 行为 |
|---|---|
| Hub 不可达 | 用**上次已应用**的块 + 启动日志告警；不删除已有块（删块=静默撤回规则） |
| Hub 返回 5xx / 超时 | 同上；重试 3 次退避（1s/3s/9s） |
| revision 变小（回滚） | 视为有效变更，正常替换块 |
| 块标记损坏 | 拒绝写入 + 明确报错（不让节点带着坏块启动） |
| 总长超限 | 拒绝注入 + 报错（**不截断**，截断会悄悄删掉规则） |

## 6. 大小与限额
- 每一层 ≤ **256 KiB**（与现有 `write_node_rules_file` 同一把尺）；
- 合并后总长 ≤ **320 KiB**：超过则**拒绝并报错**，让人去精简，而不是静默丢层。

## 7. 验收（写成可跑的用例，不写成愿望）

1. 三层齐全 → 块内三段都在，顺序 Hub → Daemon → 节点；
2. 节点层缺失（无 Daemon） → 只有 Hub + 节点两段，不报错；
3. 同 revision 重复注入 → 文件**字节不变**；
4. 用户手写内容（块外）在任何情况下都逐字节保留；
5. `[MUST NOT]` 冲突 → 以最具体层为准，provenance 记 `overridden`；
6. 只有一 个 BEGIN 或只有 END → 拒绝写入 + 报错；
7. 合并后超过 320 KiB → 拒绝 + 报错（不截断）；
8. Hub 不可达 → 保留上次块 + 告警（断言"块没有被删除"）；
9. 节点令牌不能写 Hub 规则（已由 `.152` 覆盖，作为回归）。

## 8. 待决三问（附推荐默认值）

| # | 问题 | 推荐 | 影响范围 |
|---|---|---|---|
| 1 | 冲突时以**最具体层**为准，接受吗？ | 接受（C 形态 + A 裁决） | §2.3 |
| 2 | 合并总长上限 | **320 KiB**（单层 256 KiB） | §6 |
| 3 | 是否需要「禁止覆盖」的安全键（上层 `[MUST NOT]` 不能被下层删除）？ | v1 **不做**；若要做，只允许「加严」不允许「放宽」 | §3.2 |

## 9. 明确不做
- 不改写块外的 `CLAUDE.md` / `AGENTS.md`；
- 不在运行中推送（v1）；
- 不做语义推断式的冲突合并；
- 不做执行期强制（没有"违反规则就拦下任务"这一层）；
- 不做客户端编辑页（等语义定稿）。
