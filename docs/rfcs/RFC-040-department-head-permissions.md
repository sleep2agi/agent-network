# RFC-040 部门负责人权限(组织架构 v2)

> 状态:**已接受(10-02,五条均按推荐默认)**(看板 #455,父任务 #419)。Hub 侧实现跟进中。
> 前置:v1 已上线 —— Hub .85 `network_departments` + `network_members.department_id`,每个部门一个负责人
> (`leader_user_id`);app 0.2.191「成员与部门」。v1 里只有网络 owner/admin 能改组织架构,负责人只是一个标注。

Vincent 原话(10-02):「是人类的权限,它是需要这样去做设计的,对。」#419 的 v2 计划:「负责人管本部门、项目可按部门授权,与按人授权并存」。

## 0. 结论先行

- **负责人 = 本部门子树的「小管理员」**:管人(在子树内调动、设子部门负责人)、管子部门(建 / 改名 / 删空部门)、管本部门的任务;对本部门成员的 Agent **只看不管**。
- **不新增角色**。负责人身份每次请求现算:`leader_user_id = 我` 的部门及其全部下级。撤掉负责人,权限当场消失。
- **只加不减**:负责人权限、部门项目授权都和现有的按人授权、`task_access`、Agent 授权**取并集**,不收回任何人已有的东西。
- **只增迁移**:一张新表(部门 × 项目授权),零改列;旧 app 行为不变。
- 网络级的事(邀请 / 移出成员、改角色、建项目、Agent 授权、节点启停 / 规则 / 配置)**仍只给 owner/admin**。

## 1. 权限矩阵

「本部门」= 我担任负责人的部门 + 它的全部下级部门(继承规则见 §2)。「本部门成员」= `department_id` 落在本部门里的成员。

| 动作 | owner | admin | 部门负责人 | 普通成员(member) |
|---|---|---|---|---|
| **成员** | | | | |
| 看组织架构、谁在哪个部门 | ✅ | ✅ | ✅ | ✅(v1 已如此) |
| 在本部门子树内调动成员(A 组 → B 组) | ✅ | ✅ | ✅ | ❌ |
| 把「未分配 / 其他部门」的人调进本部门 | ✅ | ✅ | ❌(见 Q2) | ❌ |
| 把本部门成员调出到「未分配 / 其他部门」 | ✅ | ✅ | ❌(调出 = 交给别人,由管理员做) | ❌ |
| 邀请 / 移出网络、改网络角色(owner/admin/member/viewer) | ✅ | ✅(不能动 owner) | ❌ | ❌ |
| 改成员的 Agent 授权、`task_access`、按人项目授权 | ✅ | ✅ | ❌ | ❌ |
| **子部门** | | | | |
| 在本部门下建子部门、改名、排序 | ✅ | ✅ | ✅ | ❌ |
| 在本部门子树内移动子部门(换上级) | ✅ | ✅ | ✅(新上级也必须在本部门里) | ❌ |
| 删除子部门(仍只能删空部门) | ✅ | ✅ | ✅ | ❌ |
| 设 / 换**子部门**负责人(人必须是本部门成员) | ✅ | ✅ | ✅ | ❌ |
| 改**自己负责的那个部门**的名字、上级、负责人 | ✅ | ✅ | ❌(归上一级负责人或管理员) | ❌ |
| **任务 / 项目** | | | | |
| 看本部门的卡(负责人是本部门成员,或负责 Agent 归本部门成员所有) | ✅ | ✅ | ✅ | 按现有规则(§3) |
| 改本部门的卡:所有字段,含改负责人(只能改成本部门成员 / 其 Agent / 自己) | ✅ | ✅ | ✅ | 按现有规则 |
| 删除本部门的卡 | ✅ | ✅ | ✅(见 Q4,记审计 + 通知卡的负责人) | 按现有规则 |
| 看 / 改「授权给本部门」的项目里的卡 | ✅ | ✅ | ✅(按授权的 `can_edit`) | 本部门成员同样获得这份授权(§3) |
| 建 / 改名 / 归档 / 删除项目;把项目授权给部门 | ✅ | ✅ | ❌ | ❌ |
| **本部门成员的 Agent / 节点**(`nodes.owner_user_id` 是本部门成员) | | | | |
| 在名册里看见、看状态与健康(降级原因) | ✅ | ✅ | ✅(见 Q3) | 按 Agent 授权 |
| 派活 / 对话 | ✅ | ✅ | 按 Agent 授权(不因负责人身份获得) | 按 Agent 授权 |
| 管理(启停、规则文件、技能、配置、日志、删除) | ✅ | ✅ | ❌ | ❌(只有节点主人和管理员) |

附带规则:

- **viewer 当负责人不获得任何管理权**(viewer 永远只读,RFC-038 §4.1 的定死语义);app 里设负责人时对 viewer 提示。
- **owner / admin 落在某个部门里**:负责人可以在子树内调动他们的部门归属,但碰不到他们的角色和权限;他们的卡负责人能看能改(与其他成员一样)。
- 负责人在自己负责的部门之外,就是一个普通成员。

## 2. 继承规则

**上级部门负责人管理整棵子树**(推荐;企业微信同样如此)。判定:

```
managed(user) = { d | d.leader_user_id = user } ∪ 它们的全部后代
```

- 一个人可以负责多个部门,取并集。
- 子部门负责人只管自己那棵子树,管不到兄弟部门和上级。
- 上下级负责人对同一个子部门的操作都允许;冲突按最后写入,记审计。
- 部门层数上限仍是 v1 的 10 层,递归按 `parent_id` 现算,不存展开结果(500 个部门以内,一次请求内存里算完)。

## 3. 和现有按人授权怎么叠加:取并集,绝不收回

今天一个人对一张卡的权限,来自 RFC-038 §9 的几条来源:网络角色 owner/admin、`task_access='all'`、`scoped` 下的「负责人是我 / 参与人有我 / 我建的 / 按人项目授权」。v2 只**再加两个来源**:

1. **部门项目授权**(新表):项目授权给部门 D(可看 / `can_edit`)⇒ D 及其下级部门的所有成员获得这份授权。
2. **负责人权限**:对本部门的卡可看、可改、可删(§1)。

```
能看(卡) = 任一来源说能看
能改(卡) = 任一来源说能改
能删(卡) = 任一来源说能删
```

- **永不收回**:部门授权、负责人身份的增删只会让「任一来源」多一个或少一个**新来源**,从不改写按人授权、`task_access`、参与人等已有来源。
  人被调出部门,只失去来自那个部门的东西;管理员当初按人给的项目授权原样还在。
- `task_access='all'` 的成员(升级前的老成员)本来就全看全改,v2 对他们没有任何可见变化。
- 卡片上的 `viewer_can` 继续只对 `scoped` 调用者出现,值是并集后的结果;`edit_fields` 只在「仅参与人」这一种来源时才带(负责人 / 部门授权给的是全字段)。
- 「本部门的卡」按**卡的负责人**判:负责人是本部门成员,或负责 Agent 的 `owner_user_id` 是本部门成员。
  不按创建者、不按参与人判(否则谁都能把卡「挂」进别的部门)。
- Agent 授权(RFC-038 §1–§8)**不受部门影响**,唯一的例外是 §1 里「负责人能看见本部门成员 Agent 的状态」:这是名册可见性上的一个并集来源,不带派活和对话。

## 4. API、迁移、旧 app 兼容

### 4.1 新表(只增)

```sql
CREATE TABLE IF NOT EXISTS network_department_project_grants (
  network_id    TEXT NOT NULL,
  department_id TEXT NOT NULL,
  project_id    TEXT NOT NULL,
  can_edit      INTEGER NOT NULL DEFAULT 0,       -- 行存在即可看
  created_by    TEXT,
  created_at    TEXT NOT NULL DEFAULT (datetime('now')),
  PRIMARY KEY (network_id, department_id, project_id)
);
```

零改列:负责人用 v1 已有的 `leader_user_id`,成员归属用已有的 `department_id`。删部门时(只能删空部门)同一事务删掉它的项目授权行。SQLite 与 PG(RFC-039)同一份 SQL;递归子树在 JS 里算,不依赖 `WITH RECURSIVE` 的方言差异。

### 4.2 接口

| 接口 | 变化 | 谁能调 |
|---|---|---|
| `GET /api/auth/me` | `networks[]` 增加 `managed_department_ids: string[]`(含下级,空数组 = 不是负责人) | 本人 |
| `GET /api/networks/:id/departments` | 每个部门增加 `viewer_can: { manage: boolean }`;响应增加 `project_grants: [{department_id, project_id, can_edit}]` | 网络成员(同 v1) |
| `POST / PATCH / DELETE /api/networks/:id/departments[/:dept]` | 授权放宽:owner/admin **或** 目标在本部门子树内的负责人。改自己负责的部门(名 / 上级 / 负责人)→ `403 department_scope_denied` | 同左 |
| `PUT /api/networks/:id/members/:uid/department` | 负责人可调:人原来在本部门、目标部门也在本部门 | 同左 |
| `GET / PUT /api/networks/:id/departments/:dept/project-grants` | **新增**。整体替换 `[{project_id, can_edit}]`;项目不属本网络 → 400,整批不写 | owner/admin |
| `GET /api/requirements?department_id=` | **新增筛选**:负责人是该部门子树成员(或其 Agent)的卡,且在调用者可见范围内 | 网络成员 |
| `GET /api/networks/:id/departments/:dept/nodes` | **新增**:本部门成员拥有的节点,只读字段(别名、状态、健康、主人) | 负责人、owner/admin |

- 越权一律 `403 department_scope_denied`,一个固定错误。部门本身对网络成员本来就可见,不存在探测问题。
- 审计:沿用 v1 的 `auditDepartment`,detail 里多一个 `via: "leader" | "admin"`;负责人删卡另记 `requirement_deleted_by_leader` 并私信卡的负责人(复用 `requirement-notify.ts` 的私信路径)。
- 负责人身份变化(换负责人、调人、改上级、改部门项目授权)后,对受影响的人调用 `closeUserStreamsInNetwork()`,让打开着的实时流按新权限重连(Agent 授权变更已是这条路)。
- MCP `requirements_*` 经同一个处理函数,自动跟着生效。节点令牌(Agent)不经过部门判定,规则不变。

### 4.3 迁移与兼容

- **只增**:一张空表 + 几个可选字段 + 两个新只读接口。没有数据迁移,没有列默认值变化,回滚到上一版 Hub(.90)安全(旧代码不读新表)。
- **老成员不变**:没设负责人、没有部门项目授权的网络,行为逐字节与今天相同(加测试钉住)。
- **旧 app**(≤0.2.191):不读新字段,负责人在旧 app 里看不到「管理本部门」入口;但 Hub 端的并集已生效 —— `scoped` 的负责人会在旧 app 的看板里多看到本部门的卡(只变宽,不变窄)。旧 app 的部门编辑页只对 owner/admin 显示,负责人用旧 app 不会误操作。
- **整体替换的 PUT**:新的 `project-grants` 是独立接口独立表,旧 app 的 `task-grants` / `agent-grants` 整体替换碰不到它(RFC-038 §8.1 同一个教训)。
- 发布顺序:Hub 先发(新字段可选、旧 app 无感)→ app 再发「管理本部门」。

## 5. 决定(10-02 已定,五条均按推荐默认)

Owner 让我们自己定,全部取推荐默认:

1. **上级负责人管理整棵子树。** 研发部负责人能管前端组、后端组。
2. **只在本部门子树内调动。** 负责人不能把「未分配 / 其他部门」的人拉进来,也不能把人调出去;跨部门进出由管理员做。
3. **本部门成员的 Agent:只看状态和健康。** 派活 / 对话仍按 Agent 授权;管理(启停、规则、配置)仍只给节点主人和管理员。
4. **负责人能删除本部门的任务卡。** 记审计,并私信卡的负责人。
5. **授权给部门的项目,子部门成员一并获得。** 只给某个小组时,直接授权给那个小组。

越权一律回一个固定的 `403 department_scope_denied`(§4.2)。

## 6. 界面(手机、电脑两套,入口只对负责人出现)

入口判据:`/api/auth/me` 的 `managed_department_ids` 非空。owner/admin 继续用现有的「设置 → 成员与部门」,不额外加入口。

**电脑 / 平板**

- 侧栏「人员」上方加一项「管理本部门」(负责多个部门时显示「管理本部门 · 3」)。点开是 v1 的「左树右详情」同一个页面,但:
  - 左边树里**只有本部门子树可编辑**,其他部门灰显只读、不能拖入拖出;
  - 右边详情多三个页签:**成员**(可在子树内拖动调人、设子部门负责人)、**任务**(看板,预置「本部门」筛选)、**Agent**(本部门成员的节点列表,只读:状态、健康、主人)。
- 任务看板的筛选条加一个「本部门」快捷筛选(只对负责人出现)。
- 越权操作在界面上直接不提供(按钮不出现),不靠后端报错来提示。

**手机**

- 「我」页加一行「管理本部门」,照企业微信:负责一个部门直接进部门页,负责多个先进列表。
- 部门页逐层点进(和 v1 通讯录同一套交互),顶部「管理」按钮只在本部门子树内出现:添加子部门、改名、删除空部门、设负责人、调整成员部门(选人 → 选目标部门,目标只列本部门子树)。
- 部门页底部两个入口:「本部门任务」(跳到任务页并带上本部门筛选)、「本部门 Agent」(只读列表)。
- 手机不做拖动,调人一律「选人 → 选部门」两步。

## 7. 测试与发布(实现时)

- 正反两个方向逐条钉矩阵:每一行都有「负责人能 / 子树外不能 / 普通成员不能 / viewer 负责人不能」的用例;SQLite 与 PG 阶梯各跑一遍。
- 兼容回放:没有负责人、没有部门授权的网络,所有现有接口的响应逐字节不变。
- 分步发:① Hub:负责人改组织架构 + `managed_department_ids`;② Hub:部门项目授权 + 任务并集 + `department_id` 筛选;③ Hub:本部门节点只读接口;④ app 电脑 / 手机「管理本部门」。每步单独可发。
