# witnessed-red 台账（2026-11-01）

## 为什么要有这张表

一条断言「红过」并不等于它有**判别力**。两种红的读数完全不同：

```text
reds == 1 且那一条就是目标   ⇒ 判别力：这条断言单独守住了这件事
reds >> 1                    ⇒ 耦合面：这个对象被 N 条断言读，改一处全红
```

`reds=49` 这种数最能说明问题：它可能是 **1 条判别力 + 48 条连坐**。
所以记 witness 时，`reds` 与「其中多少条直接读该对象」是两个不同的数，
而只有前者的最小值（1）才回答「这条断言有没有判别力」。

## 定义（可判）

```text
可隔离 witness：存在一个变异，使 reds == 1，且那一条是目标断言
连坐 witness：  reds > 1 —— 它回答「谁依赖这个对象」，不回答「谁守住了它」
```

下面这张表按这个定义给本次会话的每一个 witness 分档。**未构造出可隔离变异的，
记「未验」，不记「已验」。**

## 连坐的那几条说明了什么

5/6/9 的共同点：**同一个文件里两条断言读同一个对象**（`STATUS_REASONS` / 联合类型）。
它们都红，是因为它们都在读那个对象；而「哪一条守住了这件事」在 `reds=2` 时无法回答。

⇒ 想让它们可隔离，变异要**更小**：不是「清空整个集合」，而是「让 ① 与 ⑤ 关心的那两件事分别失效」。
例如：
- 只让「集合相等」失效而「非空」仍成立 ⇒ 加一个**同时**在常量与 push 点里的成员（① 仍绿、⑤ 仍绿 —— 这不行）
- 只让「非空」失效而「集合相等」仍成立 ⇒ 结构上不可能（清空必然让两边不等）

最后那条结论本身是信息：**⑤ 不是一条独立断言，它是 ① 在空集情形下的补丁。**
连坐不是缺陷，是「这两条守的是同一件事的两个边界」——但记录时不能写成两条判别力。

## 使用方式

新记一条 witness 时填这张表，并回答两个问题：

1. `reds` 是几？（跑完数，不估）
2. 那 `reds` 条里，有几条**直接**读被变异的对象？

`reds > 1` 时把「连坐」写出来，不要把它写成「已验证」。
