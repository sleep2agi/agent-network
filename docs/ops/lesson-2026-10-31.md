# 2026-10-31 交接：今天长出来的几条判据

> 这份不是变更日志，是**读法**。每一条都对应一次踩过的坑，坑的形状写在条目里，方便下次一眼认出同类。

## 1. 一个绿属于（被测物，测法）二元组

报告里现在会印 `measured_by`（脚本 sha256 前 12 位 + 解释器版本）。理由：口径改一次，数字就变一次，
而读者无从判断「数变了」是代码变了还是尺子变了。

同一课的另一面：**「门是绿的」有隐含主语——哪个提交上的门**。不写 ref 的绿，读起来像在说现在。

## 2. 「读不到」与「没有」必须分成两个状态

- `build-info.json`：`present` / `absent`（正常：源码检出）/ `invalid`（缺陷：写坏了）
- `/health` 的 `build_identity_note`：`not_a_git_checkout`（部署形态正常）vs `build_info_invalid`（注入写坏）
- 部署日志：`build_commit=absent`，不是留空

把它们合成一个 `null` 之后，最需要被看见的那种故障就再也不会出现在任何读数里。

## 3. 环境依赖的断言只能看到它自己那一半

今天三个测试文件红着，原因都不是被测行为：

| 症状 | 真因 | 修法 |
|---|---|---|
| `git_dirty` 应为 `null` 却断言 `false` | 本地有 `.git` 走不到 null 支；容器里走 null 支 | 两条分支各写一条断言 |
| 建目录权限报 `unsafe_secret_directory` | `mkdirSync` 吃 umask（本机 0002） | 显式 `0o700` + 补一条目录用例 |
| `EACCES: mkdir /opt/x` | 需要可写的 `/opt/x/bin`（CI 镜像里有） | 判「能不能写」而不是「是不是 root」；跳过时**打印理由** |

**共同点**：本地绿 / CI 红，或者反过来 —— 因为断言只覆盖了它跑得到的那个分支。

## 4. 探针不是免费的

为了看一个形状而**多调一次**，可能改掉被测对象的状态（`schedule_batch_interval` 那次把 revision 推进了，
打红了同一用例后面的断言）。形状断言要挂在已有的那次调用上。

## 5. 「同一文件里两段相同代码」是假证据的温床

`report_completion` 的形状我写错三次，三次同因：

1. 断言写在 `send_reply` 用例里、注释却说是 `report_completion` —— **两者形状恰好相同 ⇒ 照样绿**；
2. 挪到正确用例后立刻红；
3. 最早那次「探测」的输出其实也打在 `send_reply` 上：patch 的定位文本在两处完全相同，`replace(...,1)` 只改第一处。

> 「形状恰好相同」比「形状不同」更容易让假证据活下来 —— 因为它会一直对到该红的那天。

## 6. stdout 是契约，stderr 是日志

`prepack` 脚本往 stdout 打了一行，就把 `npm pack --json` 的 JSON 前缀污染了 ⇒ tarball 名为空 ⇒ 发布 stage 红。
解析侧现在也容忍前缀杂质，并在拿不到 JSON 时**显式 throw**。

## 7. 「装进去的目录对」≠「跑起来的是这份字节」

前者由 install 的版本比对保证；后者要进程自证。部署脚本现在断言 `/health` 的
`build_identified === true`（仅当制品里带 `build-info.json`），失败是 `stage=build_identity_absent(22)`
且**不回滚**（版本与健康都正常，回滚会把好版本换成更旧的）。

## 8. 指标要能指认「为什么这个数变了」

今天同一份覆盖率报告改过四次口径，每次都在输出里点名变化的工具：

- helper 别名（工具名藏在 `const create = (n) => mcp(…, "tool" …)` 里）
- handler 表引用（`call(toolsFor(B).send_reply, {…})`，名字后面是逗号不是括号）
- 多行箭头（定义行以 `=>` 结尾、函数体在下一行）
- **未跟踪的测试文件**（`git ls-files` 不含 `-o` ⇒ 刚写好的测试对报告不可见）

## 9. 自己造的指标报到 100% 时，先怀疑判据

我写出过一个恒真判据，把邻近口径一次性推到 88/88（覆盖一点没变）。
两次收紧（必须是函数定义 / 必须定义行本身带该工具名 / 必须就是这一个工具）才回到可信值。

## 10. 门要跟着改动范围自己出现

三次同一个跟头：改 `scripts/` 没跑接线门、发版没跑文档版式门、改 `docs-site` 没跑版本断言门。
现在 `check-diff-shape.sh` 会按 diff 内容把对应的门拉出来跑。

## 11. 只在 PR 上跑的权威套件 = main 上没有权威

`hub-provider-core.yml` 原来只有 `pull_request` 触发。两个测试文件头写着「权威验证看它」——
而对 main 的每一次提交，那句话都不成立。加上 `push: [main]` 后，**第一次运行就抓到一个真漂移**
（精确键集 4 键 vs 实际 7 键）。

## 12. 一次瞬时错误写进粘滞布尔之后，它就不再是「当前状态」

`#3166`：`sharedDisconnected` 置 true 后没有任何地方置回 false ⇒ 热切模型永久降级到重启。
一次抖动就够了。这类「状态标志其实是历史」的字段，都要问一句：**它什么时候会被清掉**。

## 13. 已发布 ≠ 用户拿到

`npm pack <pkg>@<ver>` 解开、`--version` 对、`grep` 到修复字符串 —— 这三步都做完，
才能说「修复到了用户手里」。今天对 CLI `.202` 做了一遍，对 hub `.247` 用 `build-info.json` 做了一遍。
