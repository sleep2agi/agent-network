## Product behavior evidence

1. `send_peer_reply` performs one transaction containing exact node-token
   ownership validation, terminal task update, scheduled-run terminalization,
   and one `requires_response=none` inbox result. Injected task/run failures
   roll all three data surfaces back.
2. Recipient capability is current-session authority only: every token-bound
   heartbeat writes 1 or 0, historical node snapshots are not authoritative,
   and a live SSE connection is required.
3. A task dispatched before node-id/token rotation receives an atomic
   `reply_task_not_owned` with zero writes, then exactly one legacy task marked
   `peer_reply_legacy_fallback=true` and reason `identity_changed`. A wrong
   reply target remains a hard error and never falls back.
4. Dashboard/human/hub/scheduler task origins have `from_node_id=NULL`. The Hub
   returns the distinct zero-write signal `peer_reply_origin_not_node`; the
   real sender then uses `send_reply`, terminalizes the original task, delivers
   exactly one Dashboard reply, and creates zero child task rows. It never
   attempts `send_task` to a user alias.

   deterministic SDK preload. A short terminal reply (`done`) arrived while
   the peer cooldown was armed, overwrote the capture with its own prompt,
   entered the runtime, and was ACKed without any reply egress.

## Deployment and honest limits

- Mixed-version order remains recipient-first: Hub, ordinary reply recipients
  with a current capable heartbeat and live SSE, then codex-app-server senders.
- New sender + old Hub node-to-node fallback is tested. New sender on an old
  Hub cannot use the new origin-kind signal; deployment therefore must remain
  Hub-first before any new sender is started.
- No production DB, token, node, runtime, or fleet process was read or changed.
- No live fleet rollout, production traffic cost measurement, or long-duration
  SSE outage test was performed.
- SSE emission occurs after transaction commit. Reconnect drains missed inbox
  rows, but there is no independent periodic polling guarantee.
- Legacy node-to-node fallback intentionally preserves the old two-task shape
  during mixed-version/identity-transition cases. Its production metadata makes
  the residual countable; it is not represented as atomic.
