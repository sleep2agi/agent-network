## Product behavior evidence

1. `send_peer_reply` performs one synchronous SQLite transaction containing
   exact node-token ownership validation, terminal task update, scheduled-run
   terminalization, and one `requires_response=none` inbox result. Injected
   task/run failures roll all three data surfaces back.
2. Recipient capability is current-session authority only: every token-bound
   heartbeat writes 1 or 0, the exact canonical alias is part of the query,
   historical node snapshots are not authoritative, and a live SSE connection
   is required. A second alias on the same node cannot lend capability.
3. A task dispatched before node-id/token rotation receives an atomic
   `reply_task_not_owned` with zero writes, then exactly one marked legacy
   task. A wrong reply target remains a hard error and never falls back.
4. Origin kind is decided from the persisted task before caller capability.
   Real-process fixtures prove bound and unbound receiver tokens, plus a
   legacy row whose `to_node_id` is NULL, all answer a Dashboard-origin task
   through `send_reply`: the original terminalizes, exactly one Dashboard
   reply is stored, and zero child task rows are created.
5. The real `agent-node/src/cli.ts` ran against an isolated real Hub with a
   deterministic SDK preload. A terminal peer reply entered the runtime and
   was ACKed without reply egress. Forced vendor failures remained `failed`
   through both production branches: Dashboard origin used legacy
   `send_reply`, while a node-origin task with an exact capability-advertised,
   SSE-live recipient used atomic `send_peer_reply`. Each path terminalized
   the original, stored exactly one no-response reply, created zero child
   tasks, and was independently protected against a `replied` hard-code.
6. Capability/identity downgrade remains observable through a legacy task
   carrying `peer_reply_legacy_fallback=true` and a production-computed reason.
   Ambiguous transport and identity-query failures remain pending rather than
   choosing a potentially lossy route.
7. A real node-token task was dispatched while the receiver was offline, then
   the origin session was deleted before the real receiver process drained its
   inbox. Atomic capability negotiation returned unsupported; legacy
   `send_task` returned the structured, no-write `alias_not_found`; the sender
   then used `send_reply`. The immutable original task became `replied`, exactly
   one no-response reply row was stored for the deleted origin, and no child
   task was created. Only app-level `alias_not_found` permits this second
   route; transport ambiguity and every other application rejection remain
   thrown so the pending reply is retained.
8. Every legacy wake task carries a stable, visible original-task marker:
   `[peer-reply in_reply_to=<task_id>]`. Old Hubs deduplicate `send_task` by
   sender, recipient, and content only. The marker preserves dedup for retries
   of one original task while preventing two distinct originals with the same
   reply text from colliding. A real old-Hub + real-cli fixture dispatched two
   source tasks that produced the same SDK-stub result and observed exactly
   two wake tasks, each tied to its own original task id.

## Real old-Hub wire and exact task identity

`run-legacy-wire.sh` archives and builds the actual base
`17b8223f9d7fd25fcc435b40e7fa1fc0823ea1de`, starts it on an isolated Docker
network, and sends a real MCP `tools/call` for its absent `send_peer_reply`.
The old Hub returned its real wire form:

`result.isError: MCP error -32602: Tool send_peer_reply not found`

That same old Hub exposes `get_task`. The exact-source sender reads the exact
original row by task id and classifies its immutable `from_node_id`:

- node origin (`from_node_id` non-null) -> one legacy `send_task` wake path;
- Dashboard/user origin (`from_node_id` null) -> terminal `send_reply`;
- missing, mismatched, or malformed task identity -> zero egress and the
  pending reply remains retryable.

`get_task` application rejection is also normalized to a non-app-level
`old_hub_task_identity_unavailable` error. This is intentional: the old Hub's
real `{"ok":false,"error":"task not found"}` response must not enter the
pending queue's app-level drop branch. Unit fixtures pin missing, mismatched,
undefined/non-string identity and the exact app-level rejection shape; three
independent byte-changing mutations make each acceptance/drop regression red.

Historical rows created before `from_node_id` backfill can contain NULL even
when the sender was once a node. There is no immutable evidence left to prove
that origin. The compatibility rule therefore treats NULL as non-node and uses
terminal `send_reply`, rather than consulting a mutable alias roster and
waking a potentially unrelated replacement node. This is a conservative
identity decision, not a claim that every historical NULL originated in UI.

This is not a helper-only claim. The runner starts the real source `cli.ts`
against the archived old Hub, dispatches one node-origin and one user-origin
task, and observes the resulting old-Hub task/inbox state:

`LEGACY_HUB_WIRE_PASS code=-32602 exact_task_node=task exact_task_user=reply`

`LEGACY_CLI_E2E_PASS exact_get_task node=task user=reply`

The real-cli failure matrix registers the receiver without starting it,
enqueues two ordinary node-origin tasks plus a third task, then deletes only
the third authoritative task row from the isolated old-Hub SQLite database
before starting production `cli.ts`. It proves both compatibility hazards in
one controlled run:

`LEGACY_CLI_FAILURE_PASS equal_replies=2 identity_egress=0 pending=1`

The equal replies remain distinct through the stable original-task marker.
The missing identity produces no task/reply egress and remains exactly once in
the disk-backed pending queue; it is not guessed from the live alias roster.

A byte-changing mutation changes the production `cli.ts` lookup from

## Deployment and honest limits

- No production DB, token, node, runtime, fleet process, or network endpoint
  was read or changed.
- No live fleet rollout, production traffic/cost measurement, or long-duration
  SSE outage test was performed.
- Mixed-version fallback intentionally preserves the old two-task shape only
  for an exact node-origin task. Its metadata makes that residue countable.
  Dashboard and other non-node origins use terminal `send_reply` instead.
- The old-Hub identity query is performed on every unknown-tool fallback and
  is not negatively cached. If it cannot prove the exact task origin, the
  sender does not guess from a live/stale alias roster.
- The archived old Hub exposes full `get_task` rows at network scope, including
  content/result. This is a pre-existing old-Hub authorization property that
  cannot be retrofitted by a new sender. The compatibility call uses only the
  exact task id already present in that receiver's consumed inbox and retains
  only identity fields, but it does not claim to repair the old endpoint's
  broader read scope. Current-Hub task-read hardening is a separate concern.
- A deleted origin can no longer receive a wake task. The sender uses
  terminal `send_reply` only after the Hub has explicitly rejected that
  attempted compatibility write as app-level `alias_not_found`; this is not
  a general fallback for transport errors.
- SSE emission occurs after transaction commit. Reconnect drains missed inbox
  rows, but there is no independent periodic polling guarantee.
