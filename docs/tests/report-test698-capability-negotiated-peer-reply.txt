## Product behavior evidence

1. `send_peer_reply` performs one synchronous SQLite transaction containing
   exact node-token ownership validation, terminal task update, scheduled-run
   terminalization, and one `requires_response=none` inbox result. Injected
   task/run failures roll all three data surfaces back.
2. Recipient capability is current-session authority only: every token-bound
   heartbeat writes 1 or 0, the exact canonical alias is part of the query,
   historical node snapshots are not authoritative, and a live SSE connection
   is required. A second alias on the same node cannot lend capability.
3. A task dispatched before node-id/token rotation receives an atomic
   `reply_task_not_owned` with zero writes, then exactly one marked legacy
   task. A wrong reply target remains a hard error and never falls back.
4. Origin kind is decided from the persisted task before caller capability.
   Real-process fixtures prove bound and unbound receiver tokens, plus a
   legacy row whose `to_node_id` is NULL, all answer a Dashboard-origin task
   through `send_reply`: the original terminalizes, exactly one Dashboard
   reply is stored, and zero child task rows are created.
5. The real `agent-node/src/cli.ts` ran against an isolated real Hub with a
   deterministic SDK preload. A terminal peer reply entered the runtime and
   was ACKed without reply egress. A forced vendor failure remained `failed`
   through the production legacy `send_reply` wiring rather than being
   mislabeled `replied`.
6. Capability/identity downgrade remains observable through a legacy task
   carrying `peer_reply_legacy_fallback=true` and a production-computed reason.
   Ambiguous transport and identity-query failures remain pending rather than
   choosing a potentially lossy route.

## Real old-Hub wire and exact task identity

`run-legacy-wire.sh` archives and builds the actual base
`17b8223f9d7fd25fcc435b40e7fa1fc0823ea1de`, starts it on an isolated Docker
network, and sends a real MCP `tools/call` for its absent `send_peer_reply`.
The old Hub returned its real wire form:

`result.isError: MCP error -32602: Tool send_peer_reply not found`

That same old Hub exposes `get_task`. The exact-source sender reads the exact
original row by task id and classifies its immutable `from_node_id`:

- node origin (`from_node_id` non-null) -> one legacy `send_task` wake path;
- Dashboard/user origin (`from_node_id` null) -> terminal `send_reply`;
- missing, mismatched, or malformed task identity -> zero egress and the

## Deployment and honest limits

- No production DB, token, node, runtime, fleet process, or network endpoint
  was read or changed.
- No live fleet rollout, production traffic/cost measurement, or long-duration
  SSE outage test was performed.
- Mixed-version fallback intentionally preserves the old two-task shape only
  for an exact node-origin task. Its metadata makes that residue countable.
  Dashboard and other non-node origins use terminal `send_reply` instead.
- The old-Hub identity query is performed on every unknown-tool fallback and
  is not negatively cached. If it cannot prove the exact task origin, the
  sender does not guess from a live/stale alias roster.
- SSE emission occurs after transaction commit. Reconnect drains missed inbox
  rows, but there is no independent periodic polling guarantee.
