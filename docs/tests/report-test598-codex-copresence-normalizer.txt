## Flagged app-server process-discovery correction

The production pilot exposed a safety-test gap before any second node was
mutated. Real Codex argv is shaped as `app-server -c ... -c ... --listen WS`,
while the original discovery predicate only recognized the adjacent string
`app-server --listen WS`. The pilot remained accounted because both of its
app-server PIDs were explicitly supplied, but a second flagged process could
have evaded the automatic unaccounted-process gate.

Witnessed red/green evidence:

- with the exact old production matcher, an isolated second app-server-shaped process containing intervening `-c` arguments was accepted and the test emitted `FALSE_GREEN: flagged-appserver-must-be-unaccounted` (suite rc=1)
- the corrected implementation reads NUL-delimited argv and requires exact tokens; it rejected that same process as unaccounted (rc=2)
- a second witnessed-red run added the normalizer script path as an unrelated camouflage argv token; the first correction's filename-based skip accepted it and again emitted `FALSE_GREEN` (suite rc=1)
- the final scanner skips only its exact parent and scanner PIDs (`$$` and `BASHPID`), never attacker-controlled argv text; it rejected the camouflaged process (rc=2)
- a third witnessed-red run used the upstream-valid `--listen=WS` equals form; the split-only matcher accepted it and emitted `FALSE_GREEN` (suite rc=1)
- the final option matcher recognizes exact split and equals forms for `--listen`, `--config`, `--alias`, and `--remote`; a split-only mutation turned red (rc=1)
- a mutation that restored adjacent-token matching accepted the process, so `flagged-appserver-matcher-mutation-must-be-caught` turned red (rc=1)
