#894 / #829 — cancel-flow TUI session mismatch root cause

TEST ONLY. No merge, npm publish, production change, or Hub card edit.

## What failed

The Linux native cancel-flow package reached create, then stopped before any
cancel click. The launcher had exited 0. Bridge, serve, and attach records
agreed on one generation. The daemon still rejected the launch with
`TUI session mismatch`. A later run of the same package created successfully,
so the failure was not a permanently wrong session id. The failing process
argv was not kept, so that package log alone does not prove the cause.

## Cause

`renderAttachRecordShell` records the attach shell's own pid and start ticks,
then the shell `exec`s OpenCode. `validateLaunchHealth` requires `/proc/<pid>/cmdline`
to contain `--session` and the generation as the next element. Until `exec`,
that pid is still the shell, so the class is `pre_exec` and the guard returns
`TUI session mismatch`. After `exec`, the same pid and start ticks carry
`--session <generation>` and the same guard passes. A different generation or
a single `--session=<id>` token stays `wrong_session` and must not pass.

Create and remote start/restart both used to read that cmdline once, at
launcher exit. Remote start is the manage path used when a cancelled stop is
later confirmed and the node is started again. Both now repeat the unchanged
guard only until the original deadline (35 seconds from launch, or the caller
timeout). A deadline that has already passed does not sleep and does not add
time. Nonzero launcher exits do not enter the wait.

If start still fails for this reason, the stored error is the public code
`opencode_tui_session_mismatch`. The lifecycle read returns that code.
`TUI session mismatch` and `opencode_launch_health:TUI session mismatch`
stay redacted as `lifecycle_error`.
