## What the gate executes

The Docker test starts the production `agent-network/src/node-server.ts` in
`ANET_COMMHUB_MODE=outbound-only`, over its real MCP stdio transport. The probe
sends `initialize`, `notifications/initialized`, and `tools/list`; it requires
the exact four-tool set above. It then constructs a doctor response from the
observed handshake/tool count and passes it to the production
`assertGrokCommhubMcpDoctor` parser.

That constructed response is not used as vendor compatibility evidence. In a
separate step the container runs the exact Grok 0.2.93 binary against the same
production MCP server and runtime-shaped TOML. Grok's own `mcp doctor commhub
--json` output is passed unchanged to the production parser and reports the
four exact labels shown above. No auth file is mounted or loaded for this
keyless diagnostic.

The deployed communication-dog artifact legitimately reports three tools
because it predates #693 `upload_file`. This source includes `upload_file` and
must advertise four; old-runtime evidence must not weaken the new-source gate.

## Witnessed-red mutations

1. `upload-tool-removed` deletes `commhub_upload_file` from the production
   outbound allowlist. The real `tools/list` result no longer matches and the
   probe dies at `TOOL_SET_MISMATCH`.
2. `stale-three-tool-doctor` changes the production parser requirement from
   `4 tools discovered` back to `3 tools discovered`. The exact four-tool doctor
   response is rejected at `readiness failed: 3 tools discovered`.

The unmodified probe runs before and after the mutations. Each mutation is
applied in the disposable container and production files are restored between
runs. M1 protects the tool-list contract; M2 protects the readiness parser.
Neither mutation claims to exercise a tool body.
