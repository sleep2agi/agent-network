## Implemented contract

Feishu IPC now builds one bounded runtime provenance label:

`feishu:<conversationType>:<conversationId>:<senderOpenId>`

Each wire component is ASCII-normalized, stripped of control bytes and the
`]/\\` task-envelope delimiters, and bounded to 64 characters. The existing
`feishu:` prefix remains stable for the Feishu turn security gate.

The same label is proved visible in:

1. Codex app-server `turn/start` input;
2. OpenCode shared-session REST message input;
3. Grok TUI bracketed-paste network envelope.

The existing Feishu bridge dispatch suite also proves that a response is sent
back to the originating Feishu conversation.

## Security audit — release blocker

The message/reply transport works, but existing Feishu tool isolation is not
runtime-generic:

- `checkFeishuToolDeny` is currently invoked only by the Claude SDK
  `PreToolUse` hook in `agent-node/src/cli.ts`.
- Codex app-server turns bypass that hook. An owned shared server may run with
  `approval_policy=never` and `sandbox_mode=danger-full-access`; a Feishu turn
  could therefore read node credentials or mutate files.
- Codex 0.145 exposes per-`turn/start` `approvalPolicy` and `sandboxPolicy`, but
  the generated protocol states both apply to the current **and subsequent**
  turns. `readOnly` also does not reproduce the path-level read deny for
  `.anet` credentials. It is not an equivalent drop-in guard for a shared
  human thread.
- OpenCode copresence globally denies its pinned built-in local tools, but
  deliberately enables token-bound CommHub MCP tools. Existing Feishu policy
  denies CommHub tools wholesale because the reply must travel through the
  Feishu bridge; the shared OpenCode server cannot currently enforce that
  difference per turn.
- Grok copresence uses the pinned no-I/O profile and remains within its existing
  reviewed effective-tool boundary.

Therefore green transport tests are not a claim that all three runtimes are
safe to publish with Feishu. A runtime-level security design must be signed
before Codex/OpenCode integration is released. Prompt instructions are not an
acceptable substitute for a machine-enforced tool boundary.

Candidate options sent for technical decision:

1. a separate restricted runtime/session for Feishu-origin turns;
2. an explicitly trusted allowlist-only preview boundary (still a semantic
   downgrade from current Feishu defense-in-depth);
3. a runtime-level tool broker that applies the existing channel deny policy
   before any TUI runtime tool executes.

Until that decision, keep all three candidates local and do not merge/publish.
