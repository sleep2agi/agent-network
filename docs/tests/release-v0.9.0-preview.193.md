# 0.9.0-preview.193

> 节点失败告警新增**第四类**：模型额度耗尽（`provider.quota`）—— 与前三类同性质（不会自愈、必须人处理），但**与限流分开**。

## 为什么要有这一类

`.190` 交付的告警只认三类确定性错误：

```
缺环境变量 · 二进制缺失 · 登录失效
```

额度耗尽不在这三类里。校准数据（2026-10-28，近 7 天 2825 条失败）：

| 类别 | 条数 | 占比 |
|---|---|---|
| `provider.quota` / `usage limit has been reached` | 507 | 18% |
| 限流类文案（rate limit / 429 / too many requests） | 2 | 0.07% |

`#2840` 的观察窗口里，一家族 5 个节点同时额度耗尽产生 10 条失败，**没有一条触发告警** —— 因为它们不属于任何已识别的类别。人看到的只是"任务失败"，不知道为什么。

## 为什么必须与限流分开

```
限流（rate limit / 429）  → 等几秒重试即可，会自愈
额度（provider.quota）    → 用完就是用完，只有人能处理：换 key / 充值 / 换 provider
```

这是这个告警**唯一有用的性质**：它代表"必须人处理"。把会自愈的限流并进来，等于把这条性质稀释掉 —— 收到告警的人第一反应会变成"等会儿就好"，然后不再看。

## 匹配范围刻意收窄

宽泛匹配 `额度|limit|quota` 会命中 513 条，多出来的 6 条是**任务正文在讨论额度**（假阳性）。所以只认两句原文：

```
provider.quota:
usage limit has been reached
```

# 同一版本的第二项：共享会话忙的失败分开报「排队」与「会话等待」（#2884）

> 一条任务等了 412 分钟才失败，文案只说「30 分钟」—— 因为那是**两个量**被同一个数字代表了。

## 现场

```
2026-10-27 13:54:48  created
2026-10-27 20:16:52  started     ← 排队 382 分钟
2026-10-27 20:46:57  completed   ← 会话等待 30.1 分钟
```

30 分钟是「轮到它之后等共享会话空出来」的预算。轮到它**之前**的排队，既没有上限，也没写进任何地方。

## 影响不是文案，是报表

按 `error_code` 聚合时，这 180 条（94%）都被算成「共享会话忙」，**「排队几小时」这一层被彻底掩盖**。而两层能做的处置完全不同：

| 层 | 能做什么 |
|---|---|
| 排队 | 加节点 / 减排程 / 拉间隔 —— 可操作 |
| 会话忙 | 只能等人离开 TUI —— 不可操作 |

## 改法：读时投影，不写入

`GET /runs` 与失败摘要里，当 `error_code = task_failed_busy` 时，用 `tasks.created_at → started_at → completed_at` 算出两段，**追加**在节点原文之后：

```
实测总耗时 412 分钟：排队 382 分钟（任务创建→节点开始处理）
+ 会话等待 30 分钟（节点开始处理→失败）。
失败文案里的等待上限只代表后一段，不代表总共等了多久。
```

- 节点原文保留，不覆盖
- 读不出时刻就不拆：宁可只说总计，也不硬凑一个 30 分钟

## 上线前用生产数据校验过（只读）

```
生产库 status∈(failed,cancelled) 且 result 含「共享会话/忙碌」的任务 400 条
  → 判为 task_failed_busy 400 · 漏判 0

真实那条（2026-10-27, TMA需求欧）:
  实测总耗时 412 分钟 = 排队 382 分钟 + 会话等待 30.1 分钟
```

这是拿生产全量数据跑的，不是测试夹具 —— 单测只能证明「代码按我理解的方式工作」，回放才能回答「我理解的方式和真实数据是不是一回事」。

## 本版**不做**的事

**没有**加「排队上限 fail fast」—— 那会改变派发语义，阈值需要先有数再选。实测分布已写进 `#2935`：

```
H=30min  → 7 天拦 165 条，其中 84 条本来能成功（12.0/天误杀）
H=60min  → 44 条，误杀 14（2.0/天）
H=120min → 22 条，误杀 6（0.9/天）
H=240min → 13 条，误杀 5（0.7/天）
```
