# 开 PR 前的自查清单

2026-08-13 一天之内,我(通信龙)交付了九条 PR,其中**四条的主要内容是在修自己前一轮的东西**。
每一条都是真缺陷、修得也扎实,但四条里有三条是**外部审先发现的**,不是自查出来的。

这份清单就是那几条的根因,每一项都钉着当天的真实案例 —— 不是通用建议。

---

## 1. 证据的锚点必须是**被测代码那一版**

**案发:** 三份门的报告都写着 `source_commit=92d96129…`,而那是我跑门时的 `origin/main`,
不是分支自己的 head。独审的论证很硬:92d 那一版的 `run.sh` 里**根本没有** `tests_dir_executed`
那段代码,所以报告内容 provably 不可能由它产出 —— 是个假锚点。

**自查:**
```bash
SRC=<建镜像时传进去的 build-arg,即被跑的那份字节>
grep -oE 'source_commit=[0-9a-f]{40}' <report> | sort -u   # 必须只有一个值,且等于 $SRC
git merge-base --is-ancestor "$SRC" HEAD                    # SRC 必须是 HEAD 的祖先(可相等)
git diff --name-only "$SRC" HEAD                            # 且这中间只能是 report,不能有源码/测试/Dockerfile
git show "$SRC":<被测文件> | grep -c '<报告里出现的关键输出>'   # 必须 >0
```

> 🔴 **锚点要等于 `SRC`,不是等于 `HEAD`。**
> 第一版我在这里写的是「且等于 `git rev-parse HEAD`」。**那条规则是错的,而且错得会伤好人:**
> 报告作为 **report-only 子提交**落下之后,`HEAD` 就是那个报告提交,**合法地高于 SRC**;
> stack 分支同理。按「等于 HEAD」去查,会把**正确的做法系统性判成假红**。
> (我自己在 #835 上用的正是 report-only 子提交 —— 这条规则会否掉我自己的正确做法。)
> 正确的不变量是:**锚点 == SRC,且 SRC 是 HEAD 的祖先。**

> 🔴 **但这条规则要求换一种提交结构 —— 而本仓现有做法并不是这样,这一点必须说清楚。**
>
> 我在上面把「报告作为 report-only 子提交落在 SRC 之上」写得像是既有约定。**它不是。**
> 实测 `main` 上 14 份 `docs/tests/report*`:
>
> ```
> 纯 report-only 提交          0 / 14
> 与代码/其它文件混在同一提交   14 / 14
> ```
>
> **而混在一个提交里,锚点在结构上就不可能等于被测那一版** —— 一个提交装不下自己的哈希。
> 抽样验证:`report-546-…` 落在提交 `c527a3b7`,报告内嵌的 SHA 是 `b7d1289b`,
> **是该提交的祖先**,也就是指向「改动之前」的代码。
>
> 所以本条开篇那个 bug(报告锚点指向一个不含该改动的提交)**不是一次疏忽,
> 而是现有提交结构的必然产物**。要根治只有两条路:
>
> - **报告单独成一个子提交**,落在被测提交之上(我在 #835 上用的);
> - 或者接受锚点指向父提交,但**在报告里显式写明「本报告锚定的是父提交 X,
>   本提交 Y 只增加了报告本身」**,让读者不必猜。
>
> **两条都行,但必须选一条并写出来。** 默认什么都不说时,读者无法区分
> 「锚点指向父提交是因为结构如此」和「锚点钉错了」—— 而这两者的严重性完全不同。

最后一行**既不充分、也不必要**,只是一条便宜的启发式:
它只在「输出确实以字面量形式出现在该文件里」时才成立 —— 输出可能由多个片段拼装、
来自变量、由 import 进来的 helper 发出,或由被测文件调起的另一个命令产生。
命中说明「那一版的代码**能**产出这种输出」,
不证明**这一次**的输出就来自它。要证 provenance,得靠镜像与字节的绑定
(例如把被测文件在该 commit 下的 blob 哈希传进容器、在里面重算比对),
而不是靠「字符串在那一版里出现过」。

写解释性正文提到旧锚点时,**不要写成 `key=value` 形式** —— 否则 grep 会在同一文件里
找到第二个锚点。我第一版就差点这么写。

**同一根因发作了两次,第二次是「ref 对、时机错」:**

| 次数 | 我传给 `--build-arg SOURCE_COMMIT` 的是 | 错在哪 |
|---|---|---|
| 一 | `$(git rev-parse origin/main)` | **ref 错**:那是主干,不是分支 |
| 二 | `$(git rev-parse HEAD)`,但在 `git commit` **之前**取 | **时机错**:镜像里跑的是工作区(含改动)的代码,戳进日志的却是改动前的 SHA |

第二次尤其阴:证据本身**有效**(跑的确实是新代码),但它**自称的锚点指向一个不含该改动的提交**。
校对时会看到同一份报告里出现两个不同的 `source_commit` —— 一个在抬头(对),
一个在嵌入的运行输出里(错)。

**所以顺序是固定的,不能颠倒:**

```bash
git add -A && git commit …          # 1. 先把被测改动提交掉
SRC=$(git rev-parse HEAD)           # 2. 再取 SHA —— 此刻它才真的指向被跑的那份字节
docker build --build-arg SOURCE_COMMIT="$SRC" …   # 见下:先确认你这台怎么授予 Docker
docker run  …  > run.log            # 3. 跑,证据里带上这个 SHA
#    报告作为 report-only 子提交落在 SRC 之上
```

> ⚠️ **跑 Docker 之前,先确认这台机器是怎么授予 Docker 访问的 —— 三种情况配方不同。**
> 我第一版按审查意见把命令写成了 `sg docker -c "…"`,并注明「本仓通过组切换授予」。
> **那句话对我自己这台就不成立**:
>
> ```
> id -Gn                → …,docker        ← 我在 docker 组里
> docker ps             → 可用            ← 裸命令就行
> sg docker -c 'docker ps' → 也可用        ← sg 只是无害的多余一层
> /var/run/docker.sock  → 660 root:docker
> ```
>
> 而在另一台环境上,`sg docker -c` **同样失败** —— 因为那台**连 docker 组都没有**
> (对 #828 的一次实现回应就卡在这里,它的 Docker 契约套件因此从没跑过)。
>
> 所以判据不是「用不用 `sg`」,而是先跑一行:
>
> ```bash
> id -Gn | tr ' ' '\n' | grep -qx docker && echo "在组里:裸 docker 即可" \
>   || { docker ps >/dev/null 2>&1 && echo "不在组但可用:socket 权限/rootless" \
>        || echo "跑不了 Docker —— 别把「套件没跑」写成「套件通过」"; }
> ```
>
> **第三种情况最要紧**:它意味着你写的 Docker 门在这台机器上**根本不会执行**。
> 这时唯一正确的做法是**如实标注它没跑过**,而不是把它当成已验证的证据交付。

自检一行(应当只输出一个值):

```bash
grep -oE 'source_commit=[0-9a-f]{40}' <报告> | sort -u
```

## 2. 验了零件,还要验装配

**案发:** 我把 `qa.sh` 的 build-arg 从硬编码链改成从 Dockerfile 推导,并对 7 个套件
逐个核过「推导出的参数名对不对」。**全对。** 但 `qa.sh` 是 `set -euo pipefail`,
多数套件的 Dockerfile 没有那个 `ARG` → `grep` 无命中退 1 → pipefail 传给整个命令替换 →
`set -e` 把 runner 打死在**第一个**套件上,Docker 根本没跑。

**自查:** 改了某个脚本里的一行,不算验过这个脚本。**要真跑它**,而且要覆盖
「最常见的那种输入」——这里就是「没有那个 ARG 的套件」,它占多数。

## 3. 调用方要遵守被调用物**自己写明**的契约

**案发:** 我把 `test224`(安全套件)接进 CI 时写的是裸 `docker run --rm`。
而它的 Dockerfile 第 13 行明写 *the actual gate is run with `--network none`*,
`run.sh` 会打印 *runtime executed with network disabled*。
实测:带与不带这个 flag **两次都 rc=0、都打印同一句**,差异只有时间戳。
也就是说 —— **调用方一忘,这道安全门就在网络可用时产出一份声称「网络已禁用」的绿色证据。**

**自查:** 接入任何既有套件/脚本前,先读它的 Dockerfile 头注释、README、run.sh 前 30 行,
找出它对**调用方**的要求。它自己通常不会检查这些要求(见「失效四:门的结论建立在一个它从不检查的前提上」)。

## 4. 判据的范围必须和被判对象的**实际**范围一致

**案发:** 我写的元门用「路径前缀」判一个测试是否被覆盖,而两个 runner 扫
`<pkg>/tests` 用的是 `find … -maxdepth 1`。把测试放进 `agent-network/tests/sub/`,
元门报「0 个漏网」rc=0,runner 的 find 命中 0。
**这道门正是为了防「有测试但没人跑」而造的,却在自己身上漏了同一类问题。**

**自查:** 判据里每一个「范围」(路径前缀、glob、深度、时间窗、状态集),
都要回去核**被判对象**用的是不是同一个范围。不一致就是假绿。

## 5. 断言要精确到「不合规会被拒绝」

**案发(同一处改了两次才对):**
- 第一版用子串 `root not in text` 判「门是否声明了这个扫描根」——
  把 `find` 路径改掉后,`server/src` 仍出现在注释和 FAIL 文案里,门照样绿;
- 第二版换成正则但**没有结尾锚定**,`bun test src/cli.test.ts` 也匹配 `bun test src/` ——
  范围收窄到单个文件,门却仍宣称覆盖整个目录。

**自查:** 每条断言都问一次「**能让它通过的最坏输入是什么**」,然后构造那个输入跑一次。

## 6. mutation 要跑到「曾经活下来」为止

上面第 5 条的两次,都是靠 mutation 抓出来的。**如果只跑一条 mutation 就收工,
交付的会是一道看起来很像样、实际拦不住东西的门。**

一次 mutation 全红不足以说明门是实的;**要挑不同维度**(去掉守卫 / 改窄范围 /
伪造前提 / 换一种声明形式),并且把**曾经活下来的那几条写进报告** ——
后来复核的人才知道哪里薄。

**什么时候可以停?** 标题那句「跑到曾经活下来为止」容易读成「见到一条活的就停」。
把停止条件写死:

- 至少覆盖上面四个维度**各一条**;
- **如果有一条活了下来**,那条要么补断言把它变红,要么写进报告说明为什么不补;
  **如果四个维度全红**,那不是不合格 —— 它可能说明门确实强,也可能说明维度选窄了。
  这时要在报告里**写清楚你选了哪四个维度**,让复核的人能判断这四个够不够宽;
- 补完之后**重跑全部**,不能只重跑改动的那一条。

> ⚠️ **删改测试文件的 mutation,必须在隔离工作区做**(独立 worktree 或容器内的副本),
> 并在跑完后校验原文件哈希未变。在共享 checkout 里直接删测试,一旦中途失败或被打断,
> 删除会留在别人的工作区里。本清单第 ⑪ 条(替换前证明锚点唯一、提交前做规模体检)
> 同样适用于 mutation 的改动。

## 7. 没有对照的探测,结论可能整个反过来

**案发:** 我探 26 个文档化 GET 端点,得到 1 个 404,按「404 = 文档写了但不存在」
本该报缺陷。加了一条对照:**一个根本不存在的路径返回 401,不是 404。**
说明这台服务器把未知路径统一按 401 挡掉,**404 反而是路由命中后的真实响应**。
判据无效,结论反转 —— 没有对照就会报出一个假缺陷。

**自查:** 任何「出现 X 就说明 Y」的探测,都先用一个**已知不满足 Y** 的输入跑一遍,
确认它不会也产出 X。

## 8. 临时写的扫描器,先用**已知阳性 + 已知阴性**各一条校准

**案发(一天之内三次,全在我自己写的一次性检查脚本里):**

| 扫描器 | 报了什么 | 真相 |
|---|---|---|
| 「报告锚点是否等于 HEAD~1」 | #801 ⚠ 不符 | stack 分支里有三份报告,`head -1` 抓错了文件 |
| 「docs 是否引用了 main 上不存在的路径」 | `docs/troubleshooting.md` 不存在 | 正则把 `docs-site/docs/…` 截短了 |
| 同上 | `docs/pre-pr-selfcheck.md` 不存在 | 那是 PR 自己新增的文件 |

三次全是**假阳性**,而且根因都一样:**扫描器的范围和被扫对象的实际形状不一致**
—— 就是第 4 条,只不过犯在检查器上而不是被检查物上。

危险在于方向:假阳性会让你去"修"一个不存在的问题,假阴性会让你放过真问题。
**这类一次性脚本没人审、跑一次就丢,是最容易出错又最容易被信的东西。**

**自查(两条,缺一不可):**
- **已知阳性**:构造一个你确信应该被命中的输入,确认它真的被命中
  ;
- **已知阴性**:构造一个你确信不该被命中的输入,确认它没有被命中
  (第 7 条那次 404 就是靠这条救回来的 —— 拿一个**确信不存在**的路径去探,
  发现它返回 401 而不是 404,判据当场作废)。

只跑其中一条不够:只验阳性会漏掉"什么都命中"的扫描器,
只验阴性会漏掉"什么都不命中"的扫描器 —— 而后者看起来就是一片绿。

**校准输入必须覆盖数据里真实出现的形状 —— 两条不够就加。**
这条是当天用上面的方法重扫一遍时发现的:我拿「纯路径」做了阳性和阴性各一条,
两条都通过,但扫描结果里仍有两个假阳性 —— 它们是 **GitHub URL 里的路径片段**
(`https://github.com/…/blob/main/server/src/auth.ts`),而我的校准输入里
根本没有 URL 这种形状,所以校准放行了这个盲点。

校准证明的是「在你构造的那几种输入上它是对的」,不是「它对」。

## 9. 先搞清这个计数的**单位**,再谈趋势

**案发:** 我在 hub 日志里 grep `delivered-stale`,数出 **1018 条**,还画了小时曲线
(6 → 45 → 67 条/小时),据此报了「舰队级问题,而且在上升」。

拆开看之后,那个量级是假的:

```
954 条写的是   recorded 1 delivered-stale task warning(s)
 61 条写         recorded 2 …
  3 条写         recorded 3 …
相邻两条间隔    30 / 80 / 95 / 110 / 175 / 200 秒   ← 是巡检周期在重报
```

**同一时刻通常只有 1 个卡住的任务,被巡检反复重报。** 而同一个日志文件里还有另一种行 ——
`[patrol] expired N stale task(s)` —— 那才是「任务真的黄了」,共 **109 条这样的日志行**,
跨约 15 天,**平均 0.3 条/小时**,是个低而稳定的背景率。

> ⚠️ 注意这里的单位仍然是**日志行**,不是**独立任务数**。
> 那行里的 `N` 可以大于 1,同一个任务也可能在不同巡检里被再次计入。
> 我把它写成「109 次」时,已经比原来的读法准确得多 —— 但**仍然不是任务数**。
> 要得到任务数,得按 task_id 去重,而不是数行。
> **这条本身就是本节的例子:一个数字被修正过一次之后,很容易被当成已经准确了。**

于是那条「67 条/小时」的曲线,正确读法不是「每小时 67 个任务出问题」,
而是「那一小时里几乎每次巡检都发现有一个任务卡着」—— **同一个任务卡得久,
不是 67 个任务坏掉**。严重性完全不同。

**我错在哪(两层)**

1. **只 grep 了一个字符串,没先看这个来源里一共有几种行。**
   `expired` 那种行就在同一个文件里,我从头到尾没找过它;
2. **`tail -3` 看到 3 条,就当成总共 3 次**(实际 109)——
   把「我截取的窗口」当成了「全部」。

**自查** —— 在把任何计数写进结论之前,先回答三个问题:

- **一条记录 = 一个什么?** 一个事件?一个对象?还是「某次轮询时该对象仍处于某状态」?
  重报型日志的计数 ≈ 状态持续时长 ÷ 轮询周期,**和对象个数无关**。
- **这个来源里还有别的行吗?** 先把种类列出来,再决定数哪一种:

  ```bash
  grep -oE '\[patrol\][a-z -]*' <日志> | sort | uniq -c    # 注意 \[ \] 必须转义
  ```

  > ⚠️ **前缀里的正则元字符要转义。** 我第一版写的是 `'<共同前缀>[a-z -]*'`,
  > 而真实前缀是 `[patrol]` —— 在 ERE 里那是**字符类**,匹配 p/a/t/r/o/l 中任一个。
  > 实测产出的是 `patrol`×3、`pired`×2、`tale task`×2、`recorded`×1 这样的碎片:
  > **一份看起来像模像样、实际全错的种类清单。**
  > 而本节的全部要点就是"先搞清有几种行"—— 配方本身却会给出假清单。
- **我数的是全集还是一个窗口?** `head`/`tail`/`--limit` 之后得到的数不能当总数。

**趋势比绝对值更容易骗人**:重报型计数的「上升」往往只说明「那段时间里状态持续得更久」,
而不是「发生得更多」。

## 10. 分清「它坏了」和「我用错了」

**案发:** 我把 server 单测的 4 条失败当「跨文件状态污染」的缺陷挂了四轮。
读了断言原文才发现:`toEqual(new Set([...]))` 和 `processed).toBe(1)` 都是
**在契约下正确的全局计数断言**,而 server 测试的既有契约就是每文件一个独立 DB
(`qa.sh` 的 L0 一直这么跑)。**不是缺陷,是我违反了契约。**

**自查:** 报缺陷前先读断言原文和它所属的契约。
反过来也一样:第 3 条里那个套件**声明**前提而不验证,那才是它自己的问题 ——
两者要分清,不要把自己的误用报成别人的缺陷,也不要把别人的缺陷吞成自己的误用。

## 11. 批量替换前证明锚点唯一;提交前证明产物规模合理

**案发(当天最重的一次):** 我用一句 Python 替换改文档,锚点是
`s[s.index("…"):s.index(":::")]` —— `:::` 取到的是**全文第一个**,切出来的片段
极短且多处重复,`replace` 全局命中了几百次。

```
原始    docs/RELEASE-SOP.md      355 行
推坏后                       158,627 行     ← 而且已经 push 到远端
```

已 `--force-with-lease` 回退,并从**远端侧**复验(分支与 PR head 一致、该文件
367 行、对 main 只动 2 个文件、坏提交被 0 个 ref 指向)。

**这一条和前十条不是同一类。** 前十条讲的都是「证据证不了你的主张」;
这一条讲的是**产物根本不是你以为的那个产物** —— 更前面一步,而且代价不同:
错误结论可以更正,**改坏的产物是已经推出去的事实**。

**自查:**

- 任何 `replace` / `sed -i` / 脚本改文件,**先数锚点出现几次**,不是 1 就别跑;
- `s.index(X)` 取的永远是**第一个** —— 用它切范围时,X 必须唯一;
- 提交前做一次**规模体检**,不看 diff 内容,只看形状:

```bash
wc -l <文件>                          # 改前 → 改后,增量是否合理
grep -c '<新增的关键句>' <文件>        # 应为 1
grep -vE '^\s*$' <文件> | sort | uniq -c | sort -rn | head -1   # 最高重复行
```

- 优先用**强制唯一匹配**的编辑方式;没有这种保证时,自己补上计数。

**事后还要做一件事:查同一个错有没有在别处也发生过。** 当天我用同样写法改过
另外七八个文件,逐个做了规模体检 + 重复行特征排查,确认只有那一次坏掉。
其余几处没出事**是因为锚点碰巧唯一,不是因为我做了检查** —— 方法上它们和出事
那次是同一种写法。

## 12. 改既有套件之前,先查它**是不是已经有一份被跟踪的报告**

**案发:同一条审查意见在一天里对我提了三次(#841 / #842 / #844)。**
三次都是同一句话:我改动了某个套件实际跑的东西(装依赖的方式、被扫的文档、
断言里的预期值),但 `docs/tests/report-test<N>*.txt` 还记着改动**之前**那次跑
的 `SOURCE_COMMIT` 与结果 —— 仓里因此没有新路径的留存证据。

**为什么会连着犯三次:**新建套件时我会想到「跑完要留报告」,因为报告是我自己
从零写的;改动既有套件时,那份报告已经在仓里、我根本没去看它,于是它就地过期。
**盲点不在「要不要留报告」,在「有没有意识到已经有一份」。**

自查(改任何 `tests/<suite>/` 或它的构建输入之前):

```bash
suite=test798-server-unit-ci
ls docs/tests/ | grep -F "${suite%%-*}"      # 有没有已跟踪的报告
```

有的话,这次改动必须连报告一起更新,且报告里的 `SOURCE_COMMIT` 要指向**含本次
改动**的那个 commit。

**「构建输入」比想象的宽。**这三次分别是:

| PR | 我以为只改了 | 实际改变了套件跑的东西 |
|---|---|---|
| #841 | Dockerfile 一行 | agent-node 的整个依赖图(`npm install` → `npm ci`) |
| #842 | 一个 lockfile | test745 装到的 hono 版本 |
| #844 | 两个 md 文档 | test831 扫到的 pin 数,以及它断言的预期值 |

**没有一次是我改了 `run.sh`。**判断标准不是「我动没动这个套件的目录」,是
「这个套件下次跑,看到的东西会不会不一样」。

> 🔴 **附带一条更难看的:**我在 #842 的回复里写「已记进
> `docs/pre-pr-selfcheck.md` 的待办」—— **那句话当时是假的,我没写。**
> 是第三次(#844)时回头核自己说过的话才发现的。
> 说「已记录」和真的记录之间隔着一次写文件;**汇报里出现「已记进某文档」时,
> 去把那个文档打开看一眼。**

## 13. 每一个「范围」都要先证明,再使用

**§11 是这一条的一个特例,而我在写完 §11 之后又栽了三次** —— 因为 §11 只写了
「批量替换」这一种形态,而这个毛病有很多张脸。共同点是一句话:

> **我操作的范围,比我以为的宽或窄,而两者打印出来一模一样。**

### 已经发生过的形态(每条都是实例,不是设想)

| 形态 | 实例 | 症状 |
|---|---|---|
| 替换的**匹配范围** | 全局 `replace` 把 `搜 \`"ack_inbox"\`` 换掉,连 `ack_inbox` 章节里本来正确的两处一起改了 | 改坏了正确的东西 |
| 正则的**行内范围** | 「在 \`x\` 段搜」按整行匹配,同一行里另一个锚串被套上了别人的限定 | **自己造出一条假告警** |
| 窗口的**方向** | 限定语只在锚串**之前**找,而英文写法 `grep \`串\` inside \`x\`` 在后面 | 漏判 |
| 字符类**排除** | 抓锚串的正则写 `[^\`\n]*?`,把带反引号的那几条整个漏掉 | 中文检出 24 / 英文 27,**数字对不上才发现** |
| 扫描的**树** | 在 `phase0/...` 老分支上 grep `server/src`,那儿只有 20 个 `.ts`,main 上是 106 | 结论建立在别的代码上 |
| 输出的**截断** | `head -N` 截掉了后面的发现(当天四次) | 「没有更多」其实是「没往下看」 |
| 计数的**单位** | 把「(pin, 文档) 对数」当成「引用总数」打印,139 vs 141 | 标签与数字不是一回事 |

### 为什么这类错特别难自己发现

**范围错的输出,和范围对的输出,长得一模一样。** 漏掉三条锚串时不会有任何东西
报错;多改两处时替换也照样成功;在老分支上 grep 出 0 命中,和真的 0 命中,都
打印一个 `0`。

所以它**不能靠看结果发现**,只能靠先证明范围。

### 自查:动手之前先把范围打印出来

```bash
# 替换:先数命中,再决定要不要全局
grep -c '<锚串>' <文件>          # 是 1 吗？不是就别用全局替换
# grep / 扫描:先证明分母不为零、且是你想要的那棵树
git branch --show-current        # 这是我要的分支吗
git ls-files <目录> | wc -l      # 分母是多少
# 正则:拿一条已知阳性和一条已知阴性各跑一次(§8 说的就是这件事)
# 窗口:两侧都试一遍,别只试你写代码时想到的那一侧
```

### 只描述症状的规则拦不住我 —— 这几条要有替代写法

§13 的第一版只列了七种形态,没给任何替代命令。结果:写完当天我又在其中一条
(输出的截断)上栽了两次。**「知道会漏」和「手边有个不漏的写法」是两回事。**

#### 看检查器/门的输出:别用 `head` / `tail`

```bash
#  ✘  会把 FAIL 列表的开头截掉,于是"4 条"看成"3 条"
python3 scripts/check-xxx.py . 2>&1 | tail -14

#  ✔  按标记段落取,取全
python3 scripts/check-xxx.py . 2>&1 | sed -n '/FAIL/,/^$/p'
#  ✔  或者干脆全打,再单独把计数行挑出来断言
out=$(python3 scripts/check-xxx.py . 2>&1); printf '%s\n' "$out"
printf '%s' "$out" | grep -E '^[a-z_]+=[0-9]+'
```

实测对照(一段 `FAIL: 4 条` + 四行条目 + 空行 + 一行尾部信息):

```
tail -5                     →  b / c / d / (空) / tail_info=1     ← 标题和第一条都没了
sed -n '/FAIL/,/^$/p'       →  FAIL: 4 条 / a / b / c / d          ← 完整
```

#### 搜索命令:`2>/dev/null` 会把「我的命令坏了」变成「没有结果」

```bash
#  ✘  command 是 shell 内建,xargs 找不到这个可执行文件
git ls-files docs-site | xargs command grep -ln 'xxx' 2>/dev/null
```

实测:这条**并不静默** —— 它 `rc=127`,并往 stderr 写
`xargs: command: No such file or directory`。**是那个 `2>/dev/null` 把它变哑的**,
于是空的 stdout 被我读成了「文件里没有」。

```bash
#  ✔  别在搜索上吞 stderr;要吞也先不吞地跑一次
git ls-files docs-site | xargs grep -ln 'xxx'
#  ✔  或者绕开 xargs,用 git 自己的搜索
git grep -ln 'xxx' -- docs-site
#  ✔  管道里还要留意 rc 是最后一个命令的;要判前面那个就用 PIPESTATUS 或 pipefail
```

**推广:任何一条「用来证明某物不存在」的命令,先在它一定有命中的输入上跑一次。**
这就是 §8 说的「已知阳性 + 已知阴性各一条」,只是这里的阳性用来验证**管道本身**
是通的,不是验证判据。

### 一条最省事的经验

**同一份数据用两种方法各量一次,数字对不上就说明至少有一次范围错了。**

当天三次都是这么发现的:139 vs 141(计数单位)、24 vs 27(字符类排除)、
中文有 mismatch 而英文没有(窗口方向)。**如果我只量一次,三次都会当成正确结果
发出去。**

## 14. 解冲突时,`<<<`/`>>>` 之外的「公共上下文」可能属于双方

**案发:** 我给出了一条合并解法(「冲突块取并集」),公开发在 PR 上,一轮之后干跑
才发现它会产出一个**看起来正常、实际有一个 CI job 永远不执行**的文件。

两个新增的 GitHub Actions job 长得很像,git 给出的冲突区是这样的:

```
<<<<<<< HEAD
  doc-source-pins:
    name: doc source-pin floor (Docker)
=======
  doc-claims:
    name: doc claim freshness (Docker)
>>>>>>>
    runs-on: ubuntu-latest          ← 不在冲突标记里
    timeout-minutes: 8
    steps:
      - uses: actions/checkout@v4

<<<<<<< HEAD
      …test831 的步骤…
=======
      …test846 的步骤…
>>>>>>>
```

中间那 5 行在两个 job 里**逐字相同**,所以 git 把它判成公共上下文、只留一份。
**但它语义上属于两个 job 各一份。**

于是「冲突块取并集」的结果是:

```yaml
  doc-source-pins:
    name: doc source-pin floor (Docker)     ← 到此为止
  doc-claims:
    name: doc claim freshness (Docker)
    runs-on: ubuntu-latest
    steps: …（5 个 step 全在这里)
```

`doc-source-pins` 只剩一行 `name`:没有 `runs-on`、没有 `steps`。

### 为什么这个错特别难发现

1. **它是合法 YAML。** 解析通过,GitHub 接受,job 名字出现在检查列表里、显示绿色 ——
   **一道从不执行的门,和一道执行且通过的门,在 PR 页面上长得一模一样。**
2. **换一个合并顺序,坏的是另一个 job。** 两种顺序各有一个 job 变空,互为镜像 ——
   看起来像"顺序敏感",实际两种都是坏的。
3. **当时仓库里所有的门都是绿的。** 因为没有任何一道门检查 workflow 文件本身
   (实测 `.github/`、`scripts/`、`tests/` 里 `yamllint`/`actionlint` 命中 = 0)。

### 正确解法

每个结构 = **自己的头 + 公共块(复制一份)+ 自己的体**:

```yaml
  doc-source-pins:
    name: …
    runs-on: ubuntu-latest        ← 复制
    timeout-minutes: 8
    steps:
      - uses: actions/checkout@v4
      …test831 的步骤…

  doc-claims:
    name: …
    runs-on: ubuntu-latest        ← 复制
    timeout-minutes: 8
    steps:
      - uses: actions/checkout@v4
      …test846 的步骤…
```

而**列表型的冲突块**(这里是 `on.paths`)取并集仍然是对的 —— 同一次冲突里,
不同的块要用不同的解法,不能一刀切。

### 自查

```bash
# 解完冲突之后,不要只看「有没有残留的 <<<<<<< 」
grep -c '<<<<<<<\|>>>>>>>' <file>        # 必要,但远远不够

# 结构断言:每个块都还完整吗
python3 -c "
import yaml; d=yaml.safe_load(open('.github/workflows/qa.yml'))
for k,j in d['jobs'].items():
    assert j.get('runs-on'), f'{k} 没有 runs-on'
    assert j.get('steps'),   f'{k} 的 steps 为空'
"
```

**坏掉的那版能通过 `yaml.safe_load`。** 只有后面这两条断言拦得住它。

### 这条不只发生在 YAML

任何「两个结构相邻、样板部分逐字相同」的文件都会这样:两个相似的测试用例、两个
相似的路由处理器、两段相似的 Dockerfile stage。**样板越标准,git 越可能把它判成
公共上下文,而它越可能属于双方。**

### 它和 §13 是同一族

§13 说的是「我操作的范围比我以为的宽或窄」。这条是它的一个具体形态:
**我以为解冲突的操作范围是标记之间,实际范围包含标记之外的共享行。**

## 15. 用一个「这个仓库根本不用的约定」去度量,会得到零信息的结论

**案发:** 在评估「要不要把 npm 的 `latest` 从 0.8.8 提到 0.9.0」时,我量了两个
标准指标:

```
窗口内(latest 发布至今)提交正文含 BREAKING CHANGE = 0
窗口内标题以 "Revert " 开头的提交                  = 0
```

读起来是「这 50 天里没有破坏性变更、也没有回滚过」—— 一条支持提版本的强证据。

**这两个数是空的。** 发出去之前回头验了本仓全历史:

```
全历史 2222 个提交中
  含 BREAKING CHANGE        = 0
  标题以 "Revert " 开头     = 0
```

**这个仓库从来不用这两个约定。** 我量的是「一个不存在的约定没有出现」。

### 为什么这类错特别危险

1. **它伪装成好消息。** 「没找到破坏性变更」和「没有破坏性变更」在句子里差一个词,
   在结论里差一个世界。
2. **它偏向你希望的方向。** 我当时在评估该不该提版本 —— 一个「零破坏性变更」的
   结论正好推着往前走。**用一个不适用的指标得到的空结论,几乎总是站在你原本
   倾向的那一边**,因为你不会去质疑一个支持你的数。
3. **它看起来很专业。** 引用了通行约定、给了确切数字、可复现 —— 每一条都对,
   只有前提是错的。

### 自查:量之前先证明这个指标在这里有意义

```bash
# 想用 X 作为指标之前,先问:这个仓库用 X 吗?
git log --all --grep='BREAKING CHANGE' | grep -c '^commit'     # 全历史,不是窗口内
git log --oneline --all | grep -cE '^[0-9a-f]+ Revert '

# 全历史命中为 0 → 这个指标在这里没有意义,别用它做判断
```

**分母要取全历史,不能只取你关心的窗口。** 只看窗口的话,「窗口内 0 次」和
「这个仓从来 0 次」打印出来是同一个 `0`。

### 它和 §8、§13 的关系

- §8 说的是「扫描器的范围和被扫对象不一致」;
- §13 说的是「我操作的范围比我以为的宽或窄」;
- 这条说的是**指标本身在这个语境里不存在** —— 扫描器没问题、范围也没问题,
  是被度量的那个属性压根没被记录过。

三者都会打印出一个漂亮的数字。区别在于:前两者算错了,这一条**根本没在算**。

### 那该用什么

不知道就说不知道。我在那次评估里的最终写法是:

> 不是「没有破坏性变更」,是「用现有的提交记录看不出来有没有」。

然后把判断交给一件静态方法答不了的事(一次真实的升级演练)。**承认某个问题
用手上的方法答不了,比给一个空的答案有用。**

## Shell 层的三个具体坑(当天各栽过一次)

- **反引号**:证据文本 / 提交信息里用 `` ` `` 包代码,会被当命令替换执行,**把内容吞成空**。
  一律用带引号的 heredoc(`<<'EOF'`),提交信息用 `git commit -F`。当天栽了两次,
  第二次把报告里「日志停在 X」的 X 吞没了 —— 报告在自述证据的位置是空白。
- **`git reset --hard` 之前先提交**:我为了丢弃一个 report-only 提交而 reset,
  把**还没提交的修复**一起冲掉了。靠 `grep -c` 复核得 0 才发现。
- **嵌套 heredoc 的结束标记不能同名**:内层 `<<'PY'` 会提前终结外层 `<<'PY'`,
  剩下的正文被 shell 当命令执行。

# 附:一道门可以怎样失效

上面九条是「开 PR 前查自己」。这一节是「审一道门时查它」——
把 2026-08-13 只读审计 main 上 20 道 CI 门时用过的四个角度收敛下来,
每一条都对应一个真实开出的 issue,可以照着复现。

一道门看起来是绿的,可能因为下面任何一种原因,而它们**互相独立**:

## 失效一:门根本没跑

- **形态**:门存在、写得也对,但没有任何 CI job 构建/运行它;或者触发路径不覆盖它的输入。
- **怎么查**:把门的 `COPY <源>` 逐条与 workflow 的 path 过滤比对;
  再核 workflow 里是否**同时**有 `-f <它的 Dockerfile>` 和 `docker run <那次 build 的 tag>`。
- **实例**:`#818` —— 三道**带 mutation** 的 L1 门,自己的目录不在触发路径里,
  改它们自己的 run.sh(哪怕把 `expect_red` 改成 `expect_green`)也不会触发 QA。
  同族的还有 `tests/lib/`:被 16 道门 COPY 并 source,却不在任何过滤里。

## 失效二:门跑了,但跑的东西比它声称的少

- **形态**:分母是现场数出来的,所以「文件消失」会让分母跟着缩水,门照样绿。
- **怎么查**:删掉一批被测文件(**保留 mutation 靶点所在的那个**)再跑一次。
- **实例**:`#817` —— 删掉 46 个中的 40 个,门报 `test_files=6 … RESULT: PASS`。
  `executed >= discovered` 只能抓「runner 跳过了文件」,抓不到「文件消失了」。
  修法是**绝对下限**,并写明「真删了测试就故意改这个数」。
- **注意范围**:主要是**语料型**门(遍历一批文件的)需要分母。
  场景/契约型门没有文件分母是正常的 —— 别拿这条去「修」它们。
  但**别把这句读成「非语料门就不用管分母」**:契约型门也有自己的枚举面
  (端点集、工具名集、profile 集),那一样是分母,一样会数错。
  判据是「**这道门声称覆盖了一个集合吗**」,不是「它遍不遍历文件」。

## 失效三:门跑了、也跑全了,但断言收得下不合规

- **形态**:断言在「合规」和「不合规」上都成立。
- **怎么查**:把断言指向一个**你确信应该被拒绝**的对象,看它红不红。
- **实例**:mutation 的命名断言写成 `grep -Fq '<测试名>'` ——
  而 `bun test` 对每个用例都打 `(pass) <名字>` / `(fail) <名字>`,
  于是那条用例**通过**时也会命中。A/B 实测:松版把断言指向一条不会红的用例
  仍然 `RESULT: PASS`,锚成 `^\(fail\).*<名字>` 后才 rc=1。

  > ⚠️ **换锚点的同时必须换 grep 模式。** 原式是 `grep -Fq`,`-F` 把 `^` `\(` 当**字面量**;
  > 而默认的 BRE 又会把 `\(` `\)` 当分组。这个锚定式**只在 `-E`(ERE)下**是想要的意思:
  > `grep -Eq '^\(fail\).*<名字>'`。改了模式不改 flag,断言会恒真或恒假 ——
  > 而恒真正是这一条要消除的东西。

## 失效四:门的结论建立在一个它从不检查的前提上

- **形态**:门**声明**前提(日志里写一句),而不是**验证**前提。
- **怎么查**:把那个前提破坏掉,看门红不红。
- **实例**:`#814` —— test224 是安全套件,run.sh 打印
  `runtime executed with network disabled`,但那是一行硬编码文案。
  实测带与不带 `--network none` **两次都 PASS 且打印同一句**,
  差异只有时间戳。调用方一忘,它就在网络可用时产出一份声称「网络已禁用」的绿色证据。

## 附带的第五种:被测代码没门,而不是门有问题

不是门失效,但同一次审计里出现,容易混:某段代码根本没有任何测试直接覆盖。
判据要收紧到「**有测试真的 import 它**」——只按名字 grep 会把注释里的提及也算进去。

> ⚠️ 但 **import 也不等于用到**:import 可能是未使用的、或只是类型导入,
> 扫描器照样能看见它。就算真的用了,也可能只拿它做 fixture —— 
> 一行断言都不落在它上面。import 只是把判据从「提到过」收紧到「用到过」,
> 离「验过」还差一层。要更强的判据,得看**断言是否落在该模块的行为上**
> (或直接用覆盖率工具),而不是数 import。
实例 `#819`:宽松判据下 13 个安全模块「0 个未覆盖」,收紧成 import 后命中 1 个,
再逐个导出函数看,只有 REST 写路径的 `resolveRestWriteNetworkId` 是 0 次点名。

**四种失效互相独立,查过一种不代表另一种不成立。**
`test224` 四种里中了第一种(在 `#803` 之前没人跑)和第四种(前提只声明不验证);
`test745` 中了第二种;我自己写的 `test798` 一度同时中了第二和第三种。
