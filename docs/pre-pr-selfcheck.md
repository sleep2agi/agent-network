# 开 PR 前的自查清单

2026-08-13 一天之内,我(通信龙)交付了九条 PR,其中**四条的主要内容是在修自己前一轮的东西**。
每一条都是真缺陷、修得也扎实,但四条里有三条是**外部审先发现的**,不是自查出来的。

这份清单就是那几条的根因,每一项都钉着当天的真实案例 —— 不是通用建议。

---

## 1. 证据的锚点必须是**被测代码那一版**

**案发:** 三份门的报告都写着 `source_commit=92d96129…`,而那是我跑门时的 `origin/main`,
不是分支自己的 head。独审的论证很硬:92d 那一版的 `run.sh` 里**根本没有** `tests_dir_executed`
那段代码,所以报告内容 provably 不可能由它产出 —— 是个假锚点。

**自查:**
```bash
grep -oE 'source_commit=[0-9a-f]{40}' <report> | sort -u   # 必须只有一个值
git rev-parse HEAD                                          # 且等于它
git show <anchor>:<被测文件> | grep -c '<报告里出现的关键输出>'   # 必须 >0
```
最后一行才是真判据:**那一版的代码能不能产出这份输出。**

写解释性正文提到旧锚点时,**不要写成 `key=value` 形式** —— 否则 grep 会在同一文件里
找到第二个锚点。我第一版就差点这么写。

## 2. 验了零件,还要验装配

**案发:** 我把 `qa.sh` 的 build-arg 从硬编码链改成从 Dockerfile 推导,并对 7 个套件
逐个核过「推导出的参数名对不对」。**全对。** 但 `qa.sh` 是 `set -euo pipefail`,
多数套件的 Dockerfile 没有那个 `ARG` → `grep` 无命中退 1 → pipefail 传给整个命令替换 →
`set -e` 把 runner 打死在**第一个**套件上,Docker 根本没跑。

**自查:** 改了某个脚本里的一行,不算验过这个脚本。**要真跑它**,而且要覆盖
「最常见的那种输入」——这里就是「没有那个 ARG 的套件」,它占多数。

## 3. 调用方要遵守被调用物**自己写明**的契约

**案发:** 我把 `test224`(安全套件)接进 CI 时写的是裸 `docker run --rm`。
而它的 Dockerfile 第 13 行明写 *the actual gate is run with `--network none`*,
`run.sh` 会打印 *runtime executed with network disabled*。
实测:带与不带这个 flag **两次都 rc=0、都打印同一句**,差异只有时间戳。
也就是说 —— **调用方一忘,这道安全门就在网络可用时产出一份声称「网络已禁用」的绿色证据。**

**自查:** 接入任何既有套件/脚本前,先读它的 Dockerfile 头注释、README、run.sh 前 30 行,
找出它对**调用方**的要求。它自己通常不会检查这些要求(见第 8 条)。

## 4. 判据的范围必须和被判对象的**实际**范围一致

**案发:** 我写的元门用「路径前缀」判一个测试是否被覆盖,而两个 runner 扫
`<pkg>/tests` 用的是 `find … -maxdepth 1`。把测试放进 `agent-network/tests/sub/`,
元门报「0 个漏网」rc=0,runner 的 find 命中 0。
**这道门正是为了防「有测试但没人跑」而造的,却在自己身上漏了同一类问题。**

**自查:** 判据里每一个「范围」(路径前缀、glob、深度、时间窗、状态集),
都要回去核**被判对象**用的是不是同一个范围。不一致就是假绿。

## 5. 断言要精确到「不合规会被拒绝」

**案发(同一处改了两次才对):**
- 第一版用子串 `root not in text` 判「门是否声明了这个扫描根」——
  把 `find` 路径改掉后,`server/src` 仍出现在注释和 FAIL 文案里,门照样绿;
- 第二版换成正则但**没有结尾锚定**,`bun test src/cli.test.ts` 也匹配 `bun test src/` ——
  范围收窄到单个文件,门却仍宣称覆盖整个目录。

**自查:** 每条断言都问一次「**能让它通过的最坏输入是什么**」,然后构造那个输入跑一次。

## 6. mutation 要跑到「曾经活下来」为止

上面第 5 条的两次,都是靠 mutation 抓出来的。**如果只跑一条 mutation 就收工,
交付的会是一道看起来很像样、实际拦不住东西的门。**

一次 mutation 全红不足以说明门是实的;**要挑不同维度**(去掉守卫 / 改窄范围 /
伪造前提 / 换一种声明形式),并且把**曾经活下来的那几条写进报告** ——
后来复核的人才知道哪里薄。

## 7. 没有对照的探测,结论可能整个反过来

**案发:** 我探 26 个文档化 GET 端点,得到 1 个 404,按「404 = 文档写了但不存在」
本该报缺陷。加了一条对照:**一个根本不存在的路径返回 401,不是 404。**
说明这台服务器把未知路径统一按 401 挡掉,**404 反而是路由命中后的真实响应**。
判据无效,结论反转 —— 没有对照就会报出一个假缺陷。

**自查:** 任何「出现 X 就说明 Y」的探测,都先用一个**已知不满足 Y** 的输入跑一遍,
确认它不会也产出 X。

## 8. 临时写的扫描器,先用**已知阳性 + 已知阴性**各一条校准

**案发(一天之内三次,全在我自己写的一次性检查脚本里):**

| 扫描器 | 报了什么 | 真相 |
|---|---|---|
| 「报告锚点是否等于 HEAD~1」 | #801 ⚠ 不符 | stack 分支里有三份报告,`head -1` 抓错了文件 |
| 「docs 是否引用了 main 上不存在的路径」 | `docs/troubleshooting.md` 不存在 | 正则把 `docs-site/docs/…` 截短了 |
| 同上 | `docs/pre-pr-selfcheck.md` 不存在 | 那是 PR 自己新增的文件 |

三次全是**假阳性**,而且根因都一样:**扫描器的范围和被扫对象的实际形状不一致**
—— 就是第 4 条,只不过犯在检查器上而不是被检查物上。

危险在于方向:假阳性会让你去"修"一个不存在的问题,假阴性会让你放过真问题。
**这类一次性脚本没人审、跑一次就丢,是最容易出错又最容易被信的东西。**

**自查(两条,缺一不可):**
- **已知阳性**:构造一个你确信应该被命中的输入,确认它真的被命中
  (第 7 条的 404 那次就是靠这条救回来的);
- **已知阴性**:构造一个你确信不该被命中的输入,确认它没有被命中。

只跑其中一条不够:只验阳性会漏掉"什么都命中"的扫描器,
只验阴性会漏掉"什么都不命中"的扫描器 —— 而后者看起来就是一片绿。

**校准输入必须覆盖数据里真实出现的形状 —— 两条不够就加。**
这条是当天用上面的方法重扫一遍时发现的:我拿「纯路径」做了阳性和阴性各一条,
两条都通过,但扫描结果里仍有两个假阳性 —— 它们是 **GitHub URL 里的路径片段**
(`https://github.com/…/blob/main/server/src/auth.ts`),而我的校准输入里
根本没有 URL 这种形状,所以校准放行了这个盲点。

校准证明的是「在你构造的那几种输入上它是对的」,不是「它对」。

## 9. 分清「它坏了」和「我用错了」

**案发:** 我把 server 单测的 4 条失败当「跨文件状态污染」的缺陷挂了四轮。
读了断言原文才发现:`toEqual(new Set([...]))` 和 `processed).toBe(1)` 都是
**在契约下正确的全局计数断言**,而 server 测试的既有契约就是每文件一个独立 DB
(`qa.sh` 的 L0 一直这么跑)。**不是缺陷,是我违反了契约。**

**自查:** 报缺陷前先读断言原文和它所属的契约。
反过来也一样:第 3 条里那个套件**声明**前提而不验证,那才是它自己的问题 ——
两者要分清,不要把自己的误用报成别人的缺陷,也不要把别人的缺陷吞成自己的误用。

## Shell 层的三个具体坑(当天各栽过一次)

- **反引号**:证据文本 / 提交信息里用 `` ` `` 包代码,会被当命令替换执行,**把内容吞成空**。
  一律用带引号的 heredoc(`<<'EOF'`),提交信息用 `git commit -F`。当天栽了两次,
  第二次把报告里「日志停在 X」的 X 吞没了 —— 报告在自述证据的位置是空白。
- **`git reset --hard` 之前先提交**:我为了丢弃一个 report-only 提交而 reset,
  把**还没提交的修复**一起冲掉了。靠 `grep -c` 复核得 0 才发现。
- **嵌套 heredoc 的结束标记不能同名**:内层 `<<'PY'` 会提前终结外层 `<<'PY'`,
  剩下的正文被 shell 当命令执行。
